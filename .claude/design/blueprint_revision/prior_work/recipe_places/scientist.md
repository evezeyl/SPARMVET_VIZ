# Recipe places: scientist and data scientist (2026-11-20)
Labels: READ (file:line), RAN (`tmpAI/panel/recipe_places/scientist/h.py`), REASONED. No repository file edited.

## 0. Flagged first (can change a result silently or hide a step)
F1. RAN. The recipe hash (the session key's first half) is the hash of lines `relative_path:sha256` of the entry file and every `!include`, the path taken relative to the entry file's folder (READ `app/modules/cache_keys.py:332-342`). The entry file's OWN NAME is therefore in the hash. Same bytes, renamed `x.yaml` to `x_2026-11-17.yaml`: hash 984718c70bb8 became d61d3ebb513e. Same bytes in another folder, same name: identical. Consequences: (a) a dated "copy" of an unchanged recipe is a new identity to the machine, the name is NOT only a label; (b) the hash cannot be recomputed by `sha256sum` on the bytes alone (the header of cache_keys.py:49-50 says it can: it cannot, the names enter); (c) an upload of an old recipe from an export under its dated name has the same hash only if every path inside is the same.
F2. READ+RAN. The shipped recipe includes fragments by path under a folder named after the recipe (`!include '1_test_data_ST22_dummy/wrangling/...'`, line 25-26). A dated file `name_2026-11-17.yaml` has two ways to do this: (i) shared fragments `name/...` for every dated version: editing a fragment changes ALL dated versions while their names stay; the dated name then proves nothing about content (the worst case: silent); (ii) one fragment folder per dated version: every dated save copies the folder (the include paths inside the entry file change, so even an unchanged recipe has different bytes). The brief does not say which. Whichever is chosen, the rule "a dated file is never edited" must cover its fragments.
F3. READ. The session record holds the id, the file-set hash, the data hash, source file paths and sha256, parquet paths; NO recipe text (`session_manager.py:377-392`). The export holds `data_analysis_recipe_sha256`, id, name, path, git commit, uv.lock hash, engine fingerprint (`export_handlers.py:200-230`); the PNG metadata holds id, app features, recipe sha, data hash (`:397-402`). The path is a local absolute path: it means nothing on another machine.
F4. READ (FACTS). Upload replaces silently, BLUEPRINT saves in place. Both are silent edits of what a figure depends on. A typo edit is exactly this.
F5. READ. Cached tables are keyed by the DEFINITION of the table, not by file bytes (`cache_keys.py:156-222`, 289-330); labels and descriptions stay in. So a comment edit or an edit in another table leaves cached tables valid and changes only the session key. This is correct and desirable; it means the table cache can never tell a user "the recipe changed".

## 4. (first) Science and trust: tracing a figure to the exact recipe, months later, another machine
What a reviewer needs to be able to do: take the export, find the recipe text that made the figure, and show the bytes match. Today only the export zip in the mode that carries a recipe does this, and the recipe in it is the ORIGINAL (D-0389, good). The decisive question is where an old recipe still lives when the author's file has moved on.

Never to be overwritten (my list, for Eve to accept or change):
1. A file whose dated name has been cited (exported, audited, saved in a session). Its bytes AND its fragment files.
2. The audit recipe and audit record of a session (D-0324, D-0333).
3. The session's copy of the recipe as it ran (not decided: see below).
4. An export already written.
An overwrite is acceptable on a draft that nobody has run on yet; the app cannot know that, so an overwrite button must tell the user "this file was used by N sessions / M exports" (the app knows its own sessions under `user_data`; it does NOT know the exports sent away).

Is the hash enough as identity, the dated name only for people? Not as built: F1 shows the name is inside the hash. Two honest options, both information for Eve: (A) accept that the identity is `file name + bytes + include paths` and say so in the documentation and the record (cheap, exact, but a rename re-identifies); (B) hash the resolved content (what the audit copy already does, `cache_keys.py:413-422`, PROVISIONAL), independent of names, comments and fragment layout. There would then be two hashes in use today (raw file set for sessions, canonical for audit copies), a reviewer cannot tell which one a record cites. One must be chosen and named in every record.

Minimum a reviewer can rely on, whichever place model is chosen: the session folder (or the audit folder, D-0340) keeps a COPY of the recipe file set as it ran, written when the session is created. Without it, the year-later answer depends on the lab's folder discipline. This is the V1 of the earlier study; I keep it. A model that moves old versions to a subfolder helps only if the subfolder is kept, backed up and not cleaned; a copy in the session does not depend on that.

## 1. Three stories, by model (M1 common folder read-only + own `user_data/recipes/`; M2 drafts in user data + explicit dated "export for production" into the common place, only where the deployment allows; M3 everything in the user's place, common place filled by an operator outside the app)
### S1. Lab production recipe, five users, one year, corrected twice
Recorded in all models: per session id + file-set hash + data hash; per export the same plus git commit, engine fingerprint.
- M1: the corrections are made by an operator by hand, outside the app. The author uploads `name_2026-03-01`, `_2026-07-10`, `_2026-11-02`. Each is a distinct id: the old sessions are refused on the new ones (D-0317), which is correct and loud. Wrong: operator fixes a typo in the dated file by hand (same name, new bytes): five users' sessions are now "same id, other hash": today only a warning (session_handlers.py:557-564 READ), D-0362 refusal not built. The record then says `name_2026-03-01` for a figure made on two different texts. This is the one silent case left.
- M2: the correction is a new dated file written by the app: the old one stays, nothing replaced. Good for trust. Wrong: the "typo edit may replace" rule (her d(2)) lets the same dated name change content in the common place: forbidden by what she said ("only in its own directory", D-0394), so common-place files are append-only. Only enforceable if the app refuses in the common place; an operator with file access can still bypass, so the record must carry the hash (F1 caveat) and the session copy.
- M3: five users each have their own copy: two users on "the same recipe" can hold different bytes under the same name. The lab's recipe has no single source; the figure of person A cannot be rebuilt by B without A's file. Worst for the question asked; the export from A (original recipe, D-0389) is then the only link.
What can go wrong in all: a fragment edited in place under a shared folder (F2).
### S2. One scientist's own draft that becomes the lab's recipe
- The draft has no date, edited freely, sessions made on it. Promotion = a copy with a date into the common place. Problem: the draft's sessions carry the draft's id (`name`), the lab's version has `name_2026-..`: the sessions made on the draft are refused on the lab recipe (D-0317) although the content is identical (and the hash differs by F1 anyway). The scientist's earlier figures can never be tied to the published recipe by the machine. What would tie them: the promotion step records "published from draft hash H" in the new file's `info` or a side record; then a human (or the app, as information) can say "bytes identical". Bytes can be identical only if the fragment paths are identical (F2).
- M1: drafts in `user_data/recipes/`; promotion by the operator: no record unless the operator writes it. M2: the app does it; the record can be written at the same moment: best. M3: promotion is outside the app: no record.
- Wrong in all: draft edited AFTER promotion: two files, one lineage, nothing links them. Then a reviewer asks "is the lab recipe the one you used?" and the answer rests on memory.
### S3. Audit in March, author replaces recipe in June, reopened in September from an export
- The export holds the ORIGINAL recipe (D-0389) and the audit record. On another machine the person uploads it under its dated name (D-0390). Works in M1/M2 if the dated name is unique in the common place; refused if a different file already has that name (the refusal is the right behaviour; but the user then cannot open the March file: what do they do? They need a way to open it under a labelled other place; see point 4 below).
- The June recipe is a different dated name: the March sessions are refused on it, loud. Good. Without a dated name (a demo or a draft), June has the same id, the hash differs: today a warning only.
- September: the sessions folder of the original machine may be gone; the export alone must reopen. The export therefore must contain the audit steps with the sample IDs and counts then (D-0333), the recipe file set, the data hashes. It does not contain the data (privacy), so "reopen" = recipe and steps are shown, data re-supplied by the user and checked against `data_batch_hash`.
- M3: if the recipe place of the other machine is the user's own, the upload lands there without any lab control; nothing else differs.

## 2. A typo edit that "replaces the previous file"
Runs/reads:
- Sessions: the key is `recipe_sha[:12]:data[:12]`. After the replace the old session folder still exists on disk under the old key; the new session starts under a new key; the old one is orphaned but not deleted. In the selector it will look as the same recipe (same name) with two sessions. If the user restores the old one: same id, other hash: a warning today, a refusal after D-0362. So the typo edit makes every earlier session unreachable (once D-0362 is built) or silently reused (today). Her "replace" and D-0362 are only coherent if the app tells the user, before the replace, "N sessions were made on this file; they will be refused afterwards", and the user decides.
- Cached tables: unaffected by a comment-only edit (F5): table keys come from definitions. A typo in a column name or a step changes the keys of the tables downstream and only those. Good, and invisible to the user: the cache is not a record.
- Export already sent: it holds the original bytes (D-0389) and its hash; the replaced file no longer matches, but the export stays valid. The recipient's check will show "different from the lab's file under that name". Without the dated name changing, the recipient cannot tell which is the newer; with `info.version` unchanged they cannot tell at all.
- Can the app tell a typo from a change of what the recipe does? No, by intent: the app can only tell "bytes", "resolved content" and "steps": 
  - bytes: changes for any edit, including a comment, whitespace, and a rename of the file (F1).
  - resolved content (canonical hash of the dict, already used for audit copies): ignores comments, whitespace, key order, quote style; RAN earlier (recipe_versions): comment-only edit gives identical canonical hash; changing `info.version` changes it; `x > 5` to `x >  5` inside a string expression changes it (over-alarm, harmless). Includes `info`, labels, descriptions, plot titles, colours.
  - "only the steps count" (her leaning B): a comparison must read the tier-1 and tier-2 step lists of every table and join, the join keys and types, the source/input_fields definitions (a column type or a rename is a step in effect), the data engine and plot engine, the filter expressions as strings, the audit steps, and for each plot the table it reads and its tier-3 steps. It must read through `!include`s (a changed fragment is a change of steps) and read the filter/mutate expressions as text. It would MISS: edits whose effect is in no step but changes the figure (plot aesthetics, scales, theme, seed, labels, titles, facets, colour mapping: these are what a reader looks at), `info` fields that a reader cites (version, contact, label), the order of steps if it normalises order, engine versions (outside the recipe: `engine_fingerprint`), and, unless it compares expression ASTs, two expressions with the same meaning but different text. It also cannot see the data. "Typo" is a human judgement about intent: a changed 5 to 6 is a typo or a different threshold. So: the app can report "steps identical / steps differ / only text outside the steps differs" as information. It cannot label an edit a typo, and a figure-affecting edit outside the steps (plot part) would be classed "not what the recipe does" in a steps-only rule: a silent change to a published picture. If B is adopted, the plot section must be inside "what it does", or the sentence must say "steps only, plot settings not compared".
  - One more: B decided by steps means two files with different bytes can be called "the same" by the app. Then identity for the machine is no longer the byte hash. Both hashes must be recorded (see point 3).

## 3. Dated name = version for people, hash = identity for the machine: what each record must hold
Proposed minimum (my reading of what must be there; Eve decides the list). Common to all: `recipe_id` (file stem, dated), `recipe_name_base` and `recipe_date` stored as FIELDS (never re-parsed from the name later: names with digits/underscores make a split ambiguous; ISO date at the end after the last underscore is parsable only if the date is verified to be a date), `recipe_file_set_sha256` plus the rule used (raw file set with names, or resolved content; say which), `info.version` as the author wrote it, data batch hash, app git commit/release, engine fingerprint.
- Session record: add the recipe copy (or a pointer to the audit folder copy) and which hash rule; today: id, sha, data hash, source paths+sha, no text (READ).
- Audit record: the audit recipe file carries the original's name and fingerprint (D-0328); also the original's resolved-content hash and file-set hash, the steps with sample IDs, counts removed per step and per table, reason text, date, app commit. A record without counts and IDs cannot be re-checked on a newer recipe.
- Export: today holds id, name, local path (useless elsewhere: omit or mark local), sha, data hash, commit, uv.lock hash (READ); add `recipe_date`, `info.version`, the hash rule, the audit recipe fingerprint. The export file name has no recipe id (FACTS): the label the user types is the only name; a reviewer with three zips cannot match them to recipes without opening them.
- Picture metadata (PNG `sparmvet:*`, READ `export_handlers.py:397-402`): holds id and sha; the id now contains the date, so the metadata carries both. Add the hash rule and the app commit; keep it short because it is read alone, away from the zip.
Reasoning: both are only useful if recorded together: the name says "which one the author called it", the hash says "which bytes", and a mismatch in either direction is information (same name different hash = edited in place, forbidden for a dated file; different name same bytes/resolved content = a re-save, nothing changed).

## 4a. (point 4 of the brief) Old versions moved to a subfolder: what must still be openable
Must remain openable by the app, with no extra step beyond one switch:
1. Any file that a session, an audit record or an export in this deployment names by id. The id is the file name (ADR-092), so an id in a session record must resolve to a file, in the main folder or in the old-versions folder, by the same stem. If the move changes where the file is but not its stem, sessions keep working; the path stored in records is not used for lookup (but the orchestrator rebuilds `folder/<id>.yaml` at about 10 sites: FACTS). Those sites would have to search two folders: a code change that touches every site, verified by tests that move a file mid-session.
2. Its fragment folder, if shared (F2): moving the entry file but not its fragments breaks every include path (relative to the entry file's folder). So a version moves WITH its fragment folder, and fragments of two versions cannot be shared. This is a strong argument against shared fragments.
3. Sessions made on it: restoring them must not be blocked because the file is "old": they are readable (evidence); a figure from them may be re-exported only with a visible label "old version of name, newest is X".
4. The audit recipe and record that name it.
Must not happen: the subfolder emptied by the lab, the app silently choosing the newest when a session names an old one, a switch off by default hiding the only file that a session needs (then the session shows "recipe not found" with no hint: the message must say "it may be in old versions; switch on").
Who moves the file: if the app moves it at the final save, it changes a location the user did not choose: tell them and list what was moved; if by hand: the app must cope with a file that is not there (a session pointing to a missing id) with a clear message, never a fallback to another file.
The selector: "newest per name" depends on parsing name and date; unparseable or undated names appear as their own group, shown as such, never dropped (a recipe that vanishes from a list is a silent loss). Both places in one list: label each entry with its place and whether the user can write there; the same stem in both places: show both, flagged, never pick one (D-0390 says refused on upload; at discovery by hand, a duplicate stem is possible: the app must flag it).

## Pros/cons by model, evidence class, for the science question only
- M1 (common read-only + own): + common recipes cannot be changed by the app (READ deployment docs, but BLUEPRINT writes anyway: contradiction to resolve); + own place exists in user_data (READ: one folder per deployment, no identity, so "own" = "the deployment's", not a person's: REASONED); - corrections of the common recipe happen outside the app, unrecorded; same stem in two places is possible.
- M2 (drafts + explicit dated publish): + the one model where publishing can write a record (lineage draft hash to dated file) and refuse an existing name; + matches her wish and ADR-091 gap 1 (READ); - depends on "who may publish" which needs identity (none: REASONED, ADR-091 text), so it is by deployment, not by person; a typo replace in the draft area is safe if the sessions on the draft are told.
- M3 (all in user's place): + simplest app; - no shared source, worst traceability for a lab (S1), nothing prevents two files with the same name differing.
Recommendation from this side: M2, with append-only dated files in the common place, drafts replaceable only in the user's own place with the sessions warning, a copy of the recipe file set in the session or audit folder, and one named hash rule in every record. Open for her: which hash is the identity (named in records); whether fragments are per-version; whether the comparison "what it does" includes plot settings and `info`.
