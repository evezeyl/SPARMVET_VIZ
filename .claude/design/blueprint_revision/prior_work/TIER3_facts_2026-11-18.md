# Tier 3 at the plot entry: what the app does today, and the two meanings of "T3" (facts for D-0305, D-0306)

Digest by the coordinator of a scout's read-only survey, 2026-11-18. Two code trees were READ: `dev` (the main folder) and the big recipe change (`task/engine-keys`). Nothing was run. "reasoned" marks an inference.

## The answer for the Blueprint button

**The app REFUSES a non-empty tier 3 at a plot entry, on both trees, and nothing runs it.**
- The format allows `tier3` only at a plot entry, written as `tier3: {data_engine (optional), steps: [...]}` (`libs/utils/src/utils/recipe_spec.yaml:50-71` on the branch).
- The checker refuses it when it holds steps: check P05, "the engine does not read tier3 yet, so these steps would never be applied", fix "leave tier3 empty until the engine reads it" (`recipe_check.py:49-50` and `:1021-1025` on the branch; the same refusal on `dev` for the old shape). The switch is one constant, `TIER3_READ_BY_ENGINE = False`.
- No code runs a plot's tier 3: not the orchestrator, not HOME, not the export, not the data library (grep on both trees).
- No shipped recipe holds a non-empty tier 3.
- So a button that says "write your plot-specific steps under tier 3" would today advise what the app refuses.

## What the records say (her decisions)

- D-0063 (2026-11-15): "The T3 is the data that goes to the plot BUT not the plot recipe"; Blueprint MAY author the plot entry's tier 3; steps shared by several plots belong in tiers 1 or 2.
- D-0022, D-0024 (2026-11-12): a step is written at one of tier 1 or 2 of a table or tier 3 of a plot; an optional tier 3 on the plot entry.
- D-0146 (2026-11-16): audit steps can be added at the end of each tier, 1, 2 and 3, for now.
- D-0013 (2026-11-09): the audit reaches the engine only through a forked recipe. That is what is built: at export the audit steps are written into a FORK of the join, at its tier 2 (`libs/blueprint_arch/.../t3_translator.py:273-284`), not into the plot's tier 3.
- The format spec says the engine "must read" tier 3 and that until it does the checker refuses a non-empty list (its note DEC17). The rule text `ui_implementation_contract.md:466` says "the engine runs it like any step": that sentence is not true today.
- No decision says that only the audit may write tier 3.

## Three contradictions in the present state (for her; not resolved by me)

1. Her decision D-0063 says Blueprint may author tier 3; a user doc (`docs/workflows/blueprint_architect.qmd:11, 146-152`: "BLUEPRINT writes Tiers 1 and 2 but never Tier 3") and a code comment say it never does.
2. The reader of tier 3 is not built, so the decided tier 3 cannot be used by a recipe author at all.
3. The format spec says the audit writes its filters and drops at the plot's tier 3; the code writes them into a fork at tier 2.

## The button on `dev` and on the branch

- `dev`: "Add plot wrangling" is shown on a plot node; a click shows only a notice telling the user to write `pre_plot_wrangling: !include <path>`, a key no code reads (`app/modules/wrangle_studio.py:1601-1622, 1801-1816`).
- Branch: the button, its handler and the role are gone; three tests assert that the old key and role are not supported.
- To bring it back honestly, either the reader of tier 3 is built and the checker's refusal lifted, or the button says that tier 3 is not read by the app yet.

## The two meanings of "T3" in the texts

A = the audit in HOME ("T3 / My view"). B = the recipe's tier 3 (data steps specific to one plot).
The clearest mix-ups (of about 100 places that name T3 in the docs and 100 in the UML model):
1. `config/data_analysis_recipes/templates/left_join_lesson.yaml:92-95` (branch): "Tier 3 (the steps of the audit, applied to this plot only) is written at the plot entry": B described as A.
2. `ui_implementation_contract.md:466` (a rule file): a sentence about the recipe's own T3 list inside the audit section.
3. `.claude/design/recipe_format_spec.md:7` (branch): "Tier 1/2/3 = the steps that build, reshape and finally audit a table" against its own line 503 (plot data steps).
4. `docs/workflows/blueprint_architect.qmd:11, 146-152`: "never Tier 3" (contradicts D-0063).
5. `docs/user_guide/glossary_and_feedback.qmd:16, 30`: tier 3 "does not modify the data analysis recipe" and "T3 the plot's own data" in one page.
6. `rules_data_engine.md:30-34` and `.claude/knowledge/protocol_tiered_data.md:19`: "Tier 3 (The Leaf): Interactive UI View ... handled exclusively" by the user's filters: true of A only.
7. `docs/user_guide/system_transparency.qmd:109`: "T3 never authors wrangling": true of A, false of B as decided.
The UML model uses T3 for the audit only (clear), except one note "frozen recipe, T3 baked in as real steps".
The help page of the app has no hit.
