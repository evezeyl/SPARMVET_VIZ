## 2. The mark and the list

The form of the mark is PROVISIONAL (an agent's choice, shown to her, not decided by her): one line at the top of the file, outside the `@deps` block.

    # engine: python-polars (what in this file belongs to the engine)

Two engines are joined with `+`. The test compares the line with the list.

| Kind | Meaning (PROVISIONAL classification of each file, not reviewed by her) |
|---|---|
| engine-library | Part of the library of the engine itself (`libs/transformer/src` for Polars, `libs/viz_factory/src` for plotnine). Its own place; it stays. |
| table-library | The app's own use of Polars as its table library (read and write files, hold a table, a script), or pandas for a table of the interface. Allowed for now. |
| mixed | Engine knowledge inside code that should be neutral or that belongs to the app (types, expressions, error classes, drawing). Allowed for now, to be moved. |
| names-as-data | No import of the engine library; the file holds the engine's own names or grammar as data or as text it writes. Found by hand: the test cannot find a missing one. |

Command that runs the test (from the repository root):

    ./.venv/bin/python -m pytest libs/utils/tests/test_engine_boundary.py -q

When the test fails, read its message. There are two ways out:
1. The file really needs the engine: add it to `PLACES` in `libs/utils/src/utils/engine_boundary.py` with its engine and its kind, and put the mark line at its top.
2. It does not: remove the import.

Not a way out: weakening the test or leaving a file unlisted.

## 4. The seams that exist today

| Seam | Where | What crosses |
|---|---|---|
| The one place that chooses the engine | `app/modules/engine_registry.py`, from the two-row table `libs/utils/src/utils/engines.py` | The recipe and a block go in; an entry comes out. An engine the app has no library for is refused (D-0239). |
| Entry file of the data library | `libs/transformer/src/transformer/engine_python_polars.py` | The wrangler that runs a tier. |
| Entry file of the plot library | `libs/viz_factory/src/viz_factory/engine_python_plotnine.py` | The plot factory. |
| Run of a tier | `app/modules/orchestrator.py` | A Polars LazyFrame in and out (the engine's own object, not a neutral one). |
| Action registry | `libs/transformer/src/transformer/actions/base.py` | A function on a LazyFrame; every action carries an `engine` field. |
| Component registry | `libs/viz_factory/src/viz_factory/registry.py` | A schema dictionary; every component carries an `engine` field. |
| Drawing | `libs/viz_factory/src/viz_factory/viz_factory.py`, called through the plot dispatcher of `engine_registry.py` | A Polars table in, converted to pandas inside, a plotnine object out. |
| Export | `app/handlers/export_handlers.py` | A plotnine object in, picture bytes out. |

So the dispatch exists for running a tier and drawing a plot. What crosses is still the engine's own object. Names of actions and join kinds that code outside the registry needs are read from `libs/utils/src/utils/action_names.py`, and the lineage reads `READINGS` and `FOLLOWED_JOINS` in `libs/utils/src/utils/step_effects.py`.

- Whether neutral files get a mark too. Today only files that use an engine have one.
- What pandas belongs to when no plot is drawn (the help grid).
- User-facing texts that name an engine (about 200 lines in code, hundreds in the documentation pages): not recorded by this stage.
- Helper scripts under `tests/` folders: the test does not walk `tests/` folders, so a script there that imports an engine is not listed.
- Four imports of an engine library that are never used were found and left in place, because removing them is a code change: `libs/transformer/src/transformer/registry.py` (polars), `libs/id_reconciliation/src/id_reconciliation/matcher.py` (polars), `libs/utils/src/utils/hashing.py` (polars, inside a function), `assets/scripts/recipe_pictures.py` (polars, inside a function). ## 7. Her principle (2026-11-21)

Source: these are her words of 2026-11-21 as relayed by the review session, not read by this page's builder from a file of hers. No ledger line records them: a search of `.claude/knowledge/decision_ledger.md` for "the language of the recipe will be the language of each engine" finds nothing, so they are "not recorded as a ledger line". The owner may want a ledger line for them.

"the recipe needs to be adapted to the specific of each engine ... To do exactly the same thing ... the language of the recipe will be the language of each engine". So the differences between engines are expected, not defects: a recipe is written in the language of its engine (already the rule: the engine is in the step's name and in its registry field, D-0036, D-0238). What stays a question is what the app tells the user when a recipe is moved to another engine.

New code: a source file that imports polars, plotnine, matplotlib, pandas or mizani carries the mark and is in the list (rule in `.claude/rules/rules_runtime_environment.md`, section 4).
