## O1 `id_overlap_of_the_source_files` (`overlap/sonnet_O1.py`, output `overlap/O1.out`)
1. Requirement: "the metadata is supposed to cover all the ids of the result files ..." and "this needs to be checked ... it should be corresponding" [HER WORDS D-0568]. Does that contract (the ids of each result file are contained in the metadata) hold on the demo files? The other direction (metadata ids with no line in a file) is normal.
2. Expected by her contract: for every result file of the demo, 0 ids that are absent from the metadata; the number of metadata ids absent from a file may be non-zero (for example ResFinder: 38 of the 42 metadata ids have a line, so 4 absent). If one file has ids absent from the metadata, her contract does not hold for that file on the demo. If the count on the raw text differs from the count after the recipe's declared strip, the form of the id is itself a finding.
3. Independence: a read-only script reads the source data files with a plain reader (polars, the file as text) and the recipe's own declarations (which column is the entity id in each table: the field marked `is_entity_key`, its `original_name`; which file each table reads: `source.path`; `strip`; the declared type) from my own YAML parse (PyYAML only, `paths2/sonnet_graph2.py`). No engine, no lineage code, no stored table, no recipe check. It counts the files as they are, BEFORE the tier-1 steps of the recipe (the steps need the engine); it says so. The same count on the other shipped recipes whose data files are in the repository. Load checked first (`cat /proc/loadavg`).

**Observed O1** (load 3.3; `overlap/O1.out`; the script was run twice: the second run added two sections, the null ids of the metadata and the tables with no declared id, with no change to the first counts). Five recipes have a metadata table and its file in the repository. On the demo recipe `1_test_data_ST22_dummy`: every result file has 0 ids that are absent from the metadata, on the raw text, after the declared strip and after strip and lower case (the three counts are equal): **her contract holds on the demo files, per file**. The other direction: `ResFinder` 4 of 42 metadata ids have no line (70 rows, 38 distinct ids); all other demo result files cover all 42. Form of the ids: no difference between raw, stripped and lower-cased counts anywhere; no null or empty id in the demo files. **AGREES** with the expectation. Findings beyond it: (1) `demo_abromics`: its metadata file has 30 rows, 29 distinct ids and ONE ROW WITH A NULL id; its MLST file has 15 ids, all in the metadata (14 of 29 metadata ids have no line); (2) `templates/left_join_lesson`: 2 ids of the `sequenced` file are not in the metadata (`ACC0001`, `ACC0002`): the lesson is written on purpose to show it (its description says so); (3) `2_test_data_ST22_dummy` declares no entity id; read by the column name `sample_id` (not declared): `amr_data` 0 ids outside the metadata, `plasmid_data` 0 (1 metadata id has no line); (4) `templates/e_coli` and `simple_template`: the data file is not in the repository; (5) the other recipes have no `metadata_schema`. The count is on the FILES, before the recipe's tier-1 steps.
(5b) figshare_integration (declares no entity id), read by the column name sample_id: fg_phenotypes and fg_genotypes: 0 ids outside fg_metadata, 0 metadata ids without a line (980 ids each); its metadata is a data schema, not a metadata_schema.
