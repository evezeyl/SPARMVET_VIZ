## 2. What only T0 can do, and what a removal at T0 does
- **Only T0 can:** act before the author's tier-1 steps. Real cases in the DESIGN: a value filter on a column that tier 1 reshapes or drops (demo: `phenotype` of `Summary` is turned into rows by the unpivot at tier 1 [RECIPE FILE Summary_wrangling.yaml:10-14], so at tier 1 there is no column `phenotype` to filter); and a tier-1 step that reads all rows of the table (a rank, a count per group, a head, a sample). **On the demo none of the second kind exists for the five originals with tier-1 steps** (`Summary`: unpivot, split, explode, strip, unique with the entity id in the subset; `Detailed_summary`: split, rename, cast, ratio, three filters by value; `ResFinder`: one constant column; `MLST`: select, replace, fill; `VirulenceFinder`: select, split, explode, strip, unique) [RECIPE FILE wrangling/*.yaml]. All five keep the entity id column. The three filters of `Detailed_summary_wrangling.yaml:20-34` work row by row. Two `polars_unique` steps (`Summary_wrangling.yaml:27-30`, `VirulenceFinder_wrangling.yaml:28-30`) look at other rows (reasoned, not run: they remove duplicate rows and have no effect across entities). So removing an entity before or after gives the same table. The case is theoretical on the demo; the first kind (a filter by value on `phenotype`) is real but is cleaning-like, which she said the app is not for (D-0594).
- **A removal by the entity id at T0 vs at tier 1.** At T0 the entity's real lines and its added line (if any) go before tier 1. At tier 1 they go after it. **Same table when:** tier 1 is empty (then it is one table, one line), or every tier-1 step works row by row (or, for `polars_unique`, has no effect across entities) and keeps the entity id under the same name (all five on the demo) [REASONED]. **They differ when:** tier 1 has a step that reads many rows (rank, count per group, head, z-score), or renames or drops the entity id (then at tier 1 the removal is refused by the engine where the column is absent [STUDY PATHS_AND_DERIVED_AGREED.md G20]).
- **Useful fact (REASONED):** an added line exists only for an entity that has NO real line in that table. So her words "the user can then choose to remove those that were added using the audit" (D-0602) mean the same as removing those entities from that table: a removal by the entity id removes exactly the added line, and no marker column is needed. Under (a) it works at tier 1 as long as the entity id survives tier 1.

## 3. The heart: a filter by value, and the id sets (her worry)
Her worry (D-0602): a filter placed BEFORE the completion would give wrong results. The reason (REASONED): a filter by value that removes every real line of an entity, then the completion, would re-add the entity as "not in original data", which is false (the original data had it; a step removed it).
- **(a) and (b) are both AFTER the completion.** The completion (as designed, not built) runs once, on the files as read, before any place [HER WORDS D-0602 "Question A - is as read."; STUDY CAUSE_AND_SOLUTIONS_ZEROS.md D-0589 (c) point A]. Audit steps run after it [CODE READ data_wrangler.py:92; the study quotes it]. So, as designed (not built), her worry is answered in BOTH: no audit step, at T0 or at tier 1, can come before the completion. **They do not differ on this point.**
- **A filter that removes all real lines of an entity** leaves the entity ABSENT from that table, not marked. That is right: marked = the original data lacked it; absent = a step removed it (logged). The two stay apart, which is what her use case needs ("identical id sets" is a goal for the ORIGINAL data).
- **The third check** (as designed, not built) compares the id sets of the completed tables as read, before any audit step, so it never fails because of a user's step; a failure then means a bug of the app [STUDY CAUSE_AND_SOLUTIONS_ZEROS.md D-0590 sub-section point (g) and her words "if not I think we have a bug"]. Later tables will show different id sets after a removal or filter: that is a logged consequence, not a bug. The same in (a) and (b).
- **Two real traps, same in (a) and (b), to be run when the code exists:** (1) a filter by value with the choice "remove the rows with no value" also removes the added lines of every other entity (their columns are empty): entities vanish from that table. The dialog already has this choice (ui_implementation_contract.md section 8, `na`); the user must see its consequence. (2) The author's own tier-1 steps act on the added lines. On the demo: `ResFinder` tier 1 writes `status = 'Detected'` on every line [RECIPE FILE ResFinder_wrangling_tier1.yaml:1-4], so the 4 added lines would read "Detected": an added line that looks real. `MLST` fills empty `sequence_type` with "Non Determined" [MLST_wrangling.yaml]; `MLST` and `VirulenceFinder` start with a select of fixed columns, which drops a marker column (the dry run found 20 such steps, CHANNEL M665 point 3). Only `ResFinder` has added lines on the demo (the other tables hold all 42 ids) [STUDY CAUSE_AND_SOLUTIONS_ZEROS.md D-0589 (a)]. This is a finding outside this review: report to her.
