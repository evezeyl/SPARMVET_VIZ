# Recipe versions: scientist and data scientist view (2026-11-20)

Labels: READ (file:line), RAN (scratch `tmpAI/panel/recipe_versions/scientist/h.py`), INFERRED.

## 0. Flagged first (silent or weakening reproducibility)
1. TODAY a session saved on an edited recipe only warns and opens (READ `app/handlers/session_handlers.py:557-564`). The audit steps then apply to a recipe they were not made on, and the warning wording ("may not match columns") does not say that. D-0362 already decides the refusal; until built, this is a live silent risk.
2. The session folder holds no recipe text, only hashes (READ FACTS "What already keeps old recipe content"). So once the author edits the file, the March recipe is unrecoverable from the app; R in a session proves a mismatch but cannot show what the old recipe was. Only an export bundle in reproducibility mode (resolved, comments gone) or a user zip keeps it; publication-mode export keeps no recipe at all.
3. Same-name overwrite is silent and unrestricted: upload overwrites (READ FACTS), Blueprint saves in place. Nothing records "the author fixed a join".
4. Hash identity is not uniform. R = raw bytes of files (comments count); the audit copy's hash is canonical-JSON of the resolved dict (READ `cache_keys.py:107-109, 408-417`, PROVISIONAL). RAN, same recipe in 5 variants:
   - comment-only edit: raw hash changes, canonical hash IDENTICAL (matches D-0328 "changed only in comments").
   - join key renamed: both change.
   - `x > 5` to `x >  5` (spacing inside a string expression): both change (conservative; reads as "changed in what it does", a false alarm, harmless).
   - `info.version` only changed: canonical hash CHANGES. So `info` (label, version, notes) is inside the "what it does" fingerprint: a description tweak will say "changed in what it does". Decide whether `info` is excluded; otherwise the sentence over-alarms and users learn to ignore it.
5. RAN, found while testing: PyYAML (YAML 1.1) reads an unquoted `on:` key as boolean True and `canonical_hash` then crashes (`sort_keys` on bool vs str keys). I do not know which loader the app uses for recipes (not checked; `cache_keys.py` has no yaml import). If any path hashes a PyYAML-loaded dict, a recipe with `on:` would fail or collide. INFERRED risk, cheap to check.
6. Mixed-version reports: today nothing stops a report that combines a March audit session and an April session on the same id; session_key differs (R[:12]), so they sit in separate folders, but any export or compare that groups by recipe id would blend them. INFERRED.

## 1. What makes a result defensible
A reviewer asks: which recipe, which data, which engine. Needed, provably: (a) the recipe content as it ran (full text, not only a hash: a hash proves identity only if the text is still somewhere); (b) hash of that content, with the rule to compute it written; (c) data hash (exists, `data_batch_hash`); (d) app version (D-0208: git commit in development); (e) the audit steps with reasons.
- V0: gives hash + steps; recipe text only if the user exported or the audit recipe file (decided, not built) exists. The audit recipe, being a full copy of the original plus steps, DOES carry (a) once built and written to the session folder. So V0 is defensible only for sessions that have an audit recipe on disk; a plain exploration session proves nothing about content. It only seems defensible while the folder holds hashes.
- V1: gives (a)+(b) for every session: a snapshot is the proof. Cheapest honest answer to "which recipe". Fragments (`!include`) must be in the snapshot (R covers them, READ `cache_keys.py:327-338`), or the snapshot is incomplete.
- V2: gives (a) only if the author's edits go through the app. Hand edit, upload overwrite and operator deployment bypass it (READ). It seems to give provenance but the store can have holes; a version missing from it looks like "no change". Also two files cannot share an id (READ validator `:436-442`, glob `bootloader.py:414-415`), so V2 needs a new identity concept: a large change (ADR-092 touches id = file stem).
- V3: exact and independent of the app, but only if the recipe folder is a git repo and the user commits. Nothing in a deployment guarantees it (READ: only the shipped recipes are tracked). Uncommitted edits (the typical case) are exactly the ones lost. Seems rigorous, depends on user discipline the app cannot check; also not usable by a non-git user.

## 2. Dangers
- Continuing an old audit on an OLD recipe after the author fixed an error: the user may publish from a known-wrong recipe. Under V1/V2 the app MUST say, before the choice and again in the report and export: "this recipe was changed since: [what]; the changed version fixes/does X". The app cannot know "fixed an error"; it can show the diff of what it does and the author's own note. Plain, not buried in a toast (the current warning lasts 8 s, READ).
- Mixed versions in one report: each session carries its own recipe identity; an export or report from one view uses one recipe (export already refuses when R changed since open, READ `export_handlers.py:228-247`). Keep that: never build a report from two content hashes.
- Old version on a new app: D-0207 says the app converts nothing. A snapshot opened on a newer app may be refused (renamed actions, format). That is correct, but it means V1/V2 cannot promise "reopen"; they promise "show what ran and refuse to run if the engine cannot". The snapshot must also name the app commit that made it, so the user can run the old app (D-0207's own path).
- Data changed too: R and data hash are separate; a reopen of the old recipe on new data is a second change. Show both independently (D-0186: data change is not necessarily failure, recipe change is).

## 3. Re-applying audit steps on the NEW recipe (her path)
Silent failures: (1) a step names a column renamed or removed; (2) a filter on the same column now selects other rows because the join changed (March: 2 samples removed by ID; April: IDs the same but the table has other rows or different order); (3) a "remove these samples from all tables" step whose sample still exists but whose place (a step or table) no longer exists; (4) a sample removed that the fix would have excluded anyway, or now brings back. Each step may apply without error and change the number of rows differently.
The app must show, per step, before accepting: status (applies / place missing / column missing), number of rows or samples it removes NOW against what the record says it removed then (the record must store counts and the sample IDs), and a flag when the counts differ. A side-by-side of the old audit record and the new recipe is needed: at minimum a list of steps with "then removed N: [IDs]" and "now removes M: [IDs]", plus the plain sentence from D-0328 on what changed in the recipe (it does something else / only comments). Without the old record's counts and IDs stored, a safe "add again" cannot be verified; this is a requirement on the audit record (D-0333), not on versions.
The user must also be able to see that the final figure differs from March's, and why, before exporting. Not auto-applied: a refusal plus explicit user confirmation per step (D-0362 and "software does not choose").

## 4. Version identifier a scientist can cite
- Hash alone: exact, unreadable, and meaningful only if the text is kept.
- `info.version`: readable, free text, unchecked (READ: no logic reads it; format spec says it is the author's). Mismatch detection IS possible: store, in the session or audit record, the pair (info.version, content hash). A mismatch is then: same version string, different content hash (author forgot to bump) or new version string, same content (nothing changed). RAN shows a version-only edit changes the canonical hash, so the second case can only be told if the fingerprint excludes info. Offer as information ("same version number, content changed"), never as a refusal: version is the author's word.
- Citation form I would defend: `<recipe id> <info.version> (content <first 8-12 hex of the resolved-content hash>), app <commit>`. Version for people, hash for proof; the hash is computed over the resolved content (comments excluded) so a comment fix does not change the citation. Which hash to cite (raw or resolved) must be decided once: today there are two.

## 5. Recommendation
V1 (session or audit folder keeps the snapshot of the original recipe file set as run), not V2 or V3. Reason: the proof of "which recipe" is attached to the result itself, works for every way the file can be edited, needs no change of identity or recipe-folder layout, and the audit recipe already planned is the same idea (full copy). I would not use V1 as the way to "reopen on the old recipe and continue silently": reopening is read-only evidence plus an explicit, labelled choice. V0 alone leaves exploration sessions unprovable. Not "none": D-0362 refusal stays; V1 only adds that the refusal can show what the old recipe was.
Pros: (a) proof per result [INFERRED from READ facts]; (b) no new id concept; (c) works with the app's refusal on format change. Cons: storage and fragments to include; reopening on a newer app can fail (D-0207); a stored old recipe may tempt publishing from a corrected-away error; the snapshot must be written at session creation (not later, or the edit has already happened): INFERRED, needs a check at which moment the first session file is written.
V2 pros: user sees history. Cons: holes (bypass paths), identity change, "latest proposed" invites silent drift. V3 pros: exact, outside app. Cons: not guaranteed present or committed, not for non-git users.
Shown at the moment of choosing (user decides): the old and the new recipe's dates and `info.version`; the author's change note if any; the plain sentence (does something else / comments only) with a readable list of what differs (steps, columns, joins); data same or changed; app commit of then and now; consequences: "the old version is read-only/evidence; a new session on the new recipe needs the audit re-done; old figure cannot be reproduced on this app if format changed".
