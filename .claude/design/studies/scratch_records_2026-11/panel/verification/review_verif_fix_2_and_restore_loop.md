## 3. F-A "Restore click loops without end": CONFIRMED in a real browser, and it is older than this branch

Method: Playwright, `SPARMVET_APP_FEATURES=qa`, two seeded sessions (a session with a saved audit step plus one without). `_restore_session` and `delete_session` log a line to a file in the scratch copies only. Probe at `scratchpad/probe_fa.py`; outputs `probe_new.out`, `probe_base.out`, `probe_new.log`, `probe_base.log`.

- Session WITH a saved audit step, click Restore. New tree (HEAD) and the tree of 93f39d24 give the same result. The busy flag never clears (`settled_after_click: False` after 20 s, `busy_now: True`). After the click, 36 effect runs and 36 Restore calls in ~25 s, still going at 40 s when the test ended: about 1.5 per second, with 28 to 32 "Session restored" toasts piled on screen. Both trees.
- Session WITHOUT a T3 save (`home_state` is not set in that branch): the loop is much faster. New tree: 3550 Restore calls in ~25 s, 1304 toasts on screen. Base: 1994 calls, 1735 toasts. So the builder's cause is not the whole cause. `home_state` read and set does loop. But the cause that always applies is that `_notify` (notification_utils.py: `notification_log.get()` then `.set()`) is called inside the effect `_handle_session_actions`. The effect then depends on the log it writes, the click count stays above 0, and it runs again.
- On both trees a Delete clicked on another card during the loop did not run within 5 s (`delete_calls: 0`, card still there). I did not establish why (probably the loop starves the event queue). A label edit during the loop shows 6 Restore calls in 4 s; the earlier restore repeats, so a label-triggered repeat cannot be told apart from the loop. The old restore of session A is replayed forever.
- What a user sees: after Restore the page stays busy (grey/spinner), "Session restored" toasts pile up (dozens, or over a thousand if there is no save), and the screen becomes unusable.
- Science risk, REASONED from code, not run: each iteration sets `home_state` back to the saved steps (`session_handlers.py` restore branch), so a step added after Restore would be overwritten.
- Not caused by this branch. Failed Restore, Delete and Label are better: `_tell_once` stops the loop (my browser run: a failed Delete gave exactly one toast, no loop). But the new notices inside `_restore_session` (`_tell_skipped_saves`, `_not_compared`, session_handlers.py:449 and 462) are told on EVERY iteration of this loop, so they add to the flood. They are not told once.
- The fix needs a decision: per-button click bookkeeping, as `audit_stack.py` already does with `_last_delete_clicks`, or `reactive.event`, plus `reactive.isolate()` around `_notify` and the restore. It changes behaviour, so it is a separate task with a real-browser test. No ledger line covers it (D-0165: reporting it here).
