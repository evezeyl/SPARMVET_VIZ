**Status:** ACCEPTED (2026-11-05, confirmed by @evezeyl: "it should be reproducible"; a fixed seed for tests is required). Authority: @dasharch.
**Implementation status:** IMPLEMENTED 2026-11-05 on `dev`.
**Extends:** ADR-089 (cache chain, `ENGINE_CACHE_VERSION` raised to 2), `rules_data_engine.md`, `rules_viz_factory.md`.

**Context.** Rendering all plots twice from identical inputs gave different pictures, and two builds of the same anchor had the same rows in a different order. Reports, exports and audits need the same input to give the same output. Causes found by building every collection several times and bisecting the recipe:
1. Polars runs operations on several threads and promises no row order unless asked. `summarize` (`group_by`), `drop_duplicates` (`keep="any"`), `value_counts` and `sort` (ties) were not asked to keep one. `sample` had no default seed.
2. A many-to-many join (samples x genes) returned the matches of one left row in a different order on each run. `maintain_order="left"` fixes only the order of the left table; `"left_right"` also defines the order of the matches within a left row.
3. Random scatter (`position: jitter`) had no seed.
4. plotnine treats `random_state=0` as "no seed" (`if not random_state: use the global generator`), so a default seed of 0 silently did nothing.

**Decision.**
1. **Order rules** (each has a test that states the rule on data large enough to expose a random order):
   | Action | Rule |
   |---|---|
   | `summarize` | groups in the order they first appear in the input |
   | `sort` | stable: equal keys keep their input order |
   | `join`, `join_filter` | `maintain_order="left_right"` (left order, then right order of the matches); `"right_left"` for a right join |
   | `drop_duplicates` | keeps the first row of each duplicate group, in input order (`maintain_order: false` is an explicit opt-out) |
   | `value_counts` | values in first-appearance order |
   | `sample` | fixed default seed 0; another `seed` gives another sample |
2. **Plots.** Every random component is seeded by default. `DEFAULT_RANDOM_STATE = 0` in `viz_factory.py`; a layer sets its own `random_state`; `VizFactory(random_state=...)` changes the default for a whole factory (**the handle for tests** that need a known arrangement, or a deliberately different one). **The seed is a default, never a rule:** `random_state: null` (or `random`) on a layer, or `VizFactory(random_state=None)`, asks for a different arrangement on every render, because jitter can be useful to try again. A user-facing reshuffle (with the seed recorded in the export so the report stays reproducible) is a possible later feature. **Built 2026-11-09 (#49, ADR-097):** a "Reshuffle arrangement" button next to any plot with an unpinned jitter layer draws and pins a new seed into that plot's T3 `aesthetic_override.random_state` — recorded in `effective_run.yaml` via the same `seeds_per_plot` mechanism REPRO-SEED-2 already built for the unpinned-`random` case. The seed is passed to plotnine as a numpy generator object, never as a bare number, because of the zero trap above. Routes covered: `position: jitter` and `jitterdodge` on a geom, `geom_jitter`, `position_jitter`, `position_jitterdodge`.
3. **A new action that can reorder rows** (grouping, deduplication, joins, sorting, sampling, anything with parallel execution) must state its order rule in its description and have a test of that rule. A new random component must be seeded.
4. **Guards.** `app/tests/test_anchor_determinism.py` builds every collection of the shipped test manifests several times in empty folders and requires identical rows in identical order. Each fix was switched off once and the matching test failed (including the original bug).
5. **Cache.** `ENGINE_CACHE_VERSION` is raised to "2", so anchors built with the old, unordered behaviour are rebuilt (ADR-089).
6. **Documentation.** `docs/foundations/reproducibility_same_input_same_output.qmd` explains where Polars and jitter can change a result, why, and how to remediate it for manifest authors and for tests.

**Consequences.**
- Row order of anchors is now defined, so "first 100 rows", factor levels, legends and exported data hashes no longer change between sessions.
- A manifest author who wants another jitter arrangement sets `random_state` on the layer.
- Performance: stable sort, ordered `group_by` and ordered joins are slightly slower than their unordered forms; correctness comes first. `maintain_order: false` remains available for `drop_duplicates`.
