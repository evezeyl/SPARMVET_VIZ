## ADR-091: Final configuration names, launch variables, and where each setting lives (2026-11-07)

**Status:** ACCEPTED (2026-11-07, reviewed by @evezeyl; the review decisions are listed at the end of this entry; two design gaps found during the review are open). The names were agreed with @evezeyl in chat; the entry becomes ACCEPTED when Eve has reviewed it together with the issue evezeyl/SPARMVET_VIZ#27 (the IRIDA check is evezeyl/SPARMVET_VIZ#28). Authority: @dasharch.
**Replaces:** the vocabulary table (point 1), the manifest identity and startup order (points 3 and 4) of ADR-088. ADR-088 keeps its text as history under a HISTORICAL banner; the live rules exist only here, in the new terms.
**Amends:** ADR-048 (deployment profile becomes "deployment"; its IRIDA token assumption is flagged below), ADR-052 (`manifest_selector.fixed_manifest` leaves the app features files).
**Implementation status:** IMPLEMENTED on the branch `rename/config-vocabulary` (2026-11-07, phases 0 to 9, tags `rename-phase-N`), waiting for the full retest and the merge into `dev`. Plan and phases: `.claude/tasks/outdated/config_rename_strategy.md`.

**Context.** ADR-088 fixed the three kinds of configuration but left three problems:
1. Several settings sit in the wrong file (verified in code, 2026-11-07):

   | Setting | Where it is | Problem |
   |---|---|---|
   | `default_manifest` | deployment profile | read in `bootloader.py:103`, never used |
   | `fixed_manifest` | each app features template | the code uses it (`get_default_project`), so a preset names a project; `pipeline-static` pins `1_test_data_ST22_dummy`, so a real pipeline deployment opens the test data unless the template is edited |
   | `data_ingestion_enabled` | deployment profile | a feature switch in the system file, as a one-off key |
   | `logic_access`, `persona_name` | app features templates | no code reads them |
   | branding | `deployment_name` in the profile, `theme_css` in the template | split over two files |

2. The words "profile" and "persona" are ambiguous. "Profile" means three different things in the field (Nextflow: the settings of where a run happens; Snakemake: a folder of default command-line options; Docker Compose: which optional services start). "Persona" is a UX design term for a fictional type of user, not a configuration (sources below).
3. The word "manifest" is overloaded outside the project (Kubernetes and Docker manifests, package manifests) and no replacement is free of collisions inside it (counts below).

**Decision.**

1. **Three kinds of configuration, final names.**

   | What it answers | Name | Environment variable | Folder (file = `<name>.yaml`) | Old name |
   |---|---|---|---|---|
   | Where and how it runs, folders, how data arrives, the operator's defaults | **deployment** | `SPARMVET_DEPLOYMENT` | `config/deployment/` | deployment profile, connector config, `SPARMVET_PROFILE` |
   | What the user may do | **app features** (a named set of **feature flags**) | `SPARMVET_APP_FEATURES` | `config/app_features/` (the `_template` suffix is dropped: a template is copied, these are selected as they are) | persona, app features template, `SPARMVET_PERSONA`, `config/ui/templates/` |
   | The data-to-plots definition (inputs, tier steps, joins, plots) | **data analysis recipe** | `SPARMVET_DATA_ANALYSIS_RECIPE` | `config/data_analysis_recipes/` (entry point `<name>.yaml`, its mirrored folder `<name>/`) | manifest, `SPARMVET_MANIFEST`, `config/manifests/`, `locations.manifests` |

   "App features", not "features": a feature is a data column in machine learning and a genomic annotation in bioinformatics.
2. **Variable values.** A bare name is a file in the folder of that concept; anything with a `/` or ending in `.yaml` is a path (the convention `SPARMVET_PERSONA` already has, and the one Snakemake uses for `--profile`). The prefix `SPARMVET` is a single constant in the bootloader, so renaming the application changes one line. An old variable (`SPARMVET_PROFILE`, `SPARMVET_PERSONA`, `SPARMVET_DEPLOYMENT_PROFILE`) or an old profile key (`default_persona`) stops the app at startup with a message naming the new one. There is no silent alias (ADR-077, ADR-088).
3. **Where each setting lives, and the precedence.** One home per setting. A launch variable overrides the file default for that one choice and nothing else, so the three choices stay independent (twelve-factor "granular, orthogonal controls"; Hydra overrides one config group on the command line).

   | Choice | Order, first match wins |
   |---|---|
   | deployment file | `SPARMVET_DEPLOYMENT`, then `~/.sparmvet/deployment.yaml`, then `/etc/sparmvet/deployment.yaml`, then the development fallback (ADR-048 chain, file names updated) |
   | app features | `SPARMVET_APP_FEATURES`, then `default_app_features` in the deployment file, otherwise a fatal startup error |
   | data analysis recipe | `SPARMVET_DATA_ANALYSIS_RECIPE`, then `default_data_analysis_recipe` in the deployment file, then the data analysis recipe selector when the app features show it, then the empty state (ADR-087), otherwise a fatal startup error naming both keys |

   The old `fixed_manifest` leaves the app features files: a preset names no data analysis recipe. A features file that still carries it, or a deployment file that still carries `default_manifest`, stops the app at startup with the migration message. The deployment key `default_data_analysis_recipe` finally takes effect (the old key was read and never used). Whether the user may choose a recipe (the selector, formerly `manifest_selector`, now `data_analysis_recipe_selector`) stays an app features flag, because it describes a type of user. A recipe is identified by its file name without `.yaml` in the location `data_analysis_recipes` (formerly `locations.manifests`); the entry point and its mirrored folder belong together as before (basename mirroring).
4. **Path expansion.** Every path in the deployment file accepts `~` and `${VAR}`. After expansion, a path that still contains `$` stops the app at startup with the name of the unset variable (Python's `os.path.expandvars` leaves an unset reference unchanged, so without this check a typo would become a folder called `${HOME}`). This solves "each person starts their own copy on their own computer". It does not give one web user a folder of their own on a shared server: the server process has one home directory, and Shiny for Python has no built-in login. That needs the system to supply the identity (Galaxy offers the user id and e-mail to the tool, Posit Connect a username in the session). It is a connector task for later, not a configuration key.
5. **"Persona" is retired for the application.** In code, configuration, rules, docs and tests the word is replaced by "app features"; in prose that describes a type of user, "user type" is used. `PersonaValidator` becomes `AppFeaturesValidator` and `persona_manager`-style names follow the table in the issue. The word stays only for the two AI agent role files under `.claude/rules/` (`dasharch.md`, `rules_persona_bioscientist.md`), written "AI agent persona" so the two meanings cannot be confused. Claude Code's own documentation calls such a definition a "subagent" (a Markdown file whose body is the system prompt), not a persona; ours are role instructions read as rules, so "agent role" is the better word. Renaming them is optional and left to Eve (open point 4).
6. **Dead and vestigial keys are deleted, not renamed.** `logic_access`, `persona_name` and the vestigial `data_import_panel_visible` (task LEGACY-DATAIMPORT-FLAG-1) go now. An inventory of every key in the deployment files and the app features files, each marked used, unused or in the wrong home, is produced first (read-only) and reviewed by Eve before any deletion.
7. **One pass, no hybrid.** The rename of points 1 to 6 and the rename of "manifest" to "data analysis recipe" run together, in one scripted pass and one issue. After it, code, class and module names, folder and file names, configuration keys, user interface labels, rules, docs, tests and tooling use the same words; a half-renamed state (for example folders still called `manifests/` while the variable says recipe) is not allowed to reach a shared branch. Everything with the old word is in scope, including:
   - folders and files: `config/manifests/`, `assets/template_manifests/`, `rules_manifest_structure.md`, `manifest_data_contract_rules.md`, `manifest_validator.py`, `manifest_navigator.py`, the audit scripts and report names (`audit_manifest_*`), `persona_*` design and knowledge files, `config/ui/templates/`;
   - classes and keys: `ManifestNavigator`, `join_manifests`, `manifest_selector`, `locations.manifests`, `default_manifest`, `manifest_sha256`, `PersonaValidator`;
   - the gallery bundle (`recipe_manifest.yaml`, `recipe_meta.md`) takes the full name too, for example `data_analysis_recipe.yaml`, so the bare word "recipe" is free;
   - the inner uses of "recipe" are renamed in the same run so the long name cannot be shortened into a collision: the `recipe:` step list becomes `steps:`, the T3 "recipe" becomes audit steps, the "Filter Recipe Builder" becomes the filter builder, `t3_recipe_engine.py` follows, `TransformationRecipe` is decided in the mapping table.
   Stored formats change (YAML files, `manifest_sha256` in sessions and exports, saved sessions and audit files, gallery bundles). A migration script rewrites shipped files and an error that names the fix handles old files and old sessions (ADR-083 precedent, `migrate_plot_specs.py --apply`). Immutable history is exempt and marked: old ADR text, archived task files, audit logs, `docs/_freeze/`; the vocabulary note at the top of this log maps old words to new. Rough size (2026-11-07): about 290 tracked paths contain "manifest" (most are generated audit reports), 13 contain "persona", 76 contain "recipe"; word counts: manifest 2414 (one meaning), recipe 791 (four meanings), persona in 51 Python files and 87 doc and rule files.
8. **Mechanics.** As ADR-088 point 2: a script lists every use with its meaning, the mapping table (words, paths, keys) is approved by Eve before any change, files move with `git mv`, replacements run as a dry run first, and a check proves that no old word is left in a live file or path outside the exclusions (the two AI agent files, immutable history). The check stays in the repository as an audit so the old words cannot return. Because there is no second pass, every open point below is decided before the run.

**Names considered and rejected.**

| Name | Why not |
|---|---|
| one variable that names everything (a profile that contains the features) | a copy of the profile for each feature set on the same machine; the combinatorial explosion twelve-factor warns about |
| a third "project" file | the recipe already is the project file: it names its datasets and data paths |
| a launch file that composes the other three (Hydra style) | one more layer; named setups belong in a launcher outside the configuration |
| `profile`, `persona`, `template`, `environment` | see Context 2; "environment" is also the Python environment, and twelve-factor discourages named bundles |
| `features`, `feature set` alone | a data column or genomic feature in this field |
| `recipe` alone, `project`, `pipeline`, `workflow`, `blueprint`, `study` | four internal meanings; `project_root` and IRIDA's `project_id`; the upstream program; Galaxy's term; a user space; ENA/ISA metadata object (not checked) |
| `data_processing_recipe`, `analysis_recipe` | the first leaves the plots out; the second may collide with IRIDA analysis objects (not checked) |

**External checks (2026-11-07).** Confirmed: twelve-factor config (12factor.net/config); Hydra config groups and command-line overrides (hydra.cc); Galaxy tool XML `<environment_variables>` reach the container (Galaxy training material); `os.path.expandvars` leaves unset references unchanged (docs.python.org); `profile` in Nextflow, Snakemake and Docker Compose; persona as a UX design term; Kubernetes ConfigMap and manifests. **Not confirmed:** that IRIDA injects an OAuth2 token into the container at launch (the IRIDA documentation found describes the password grant for command-line tools and the `authorization_code` flow for web services; ADR-048's `SPARMVET_IRIDA_TOKEN` design must be checked with someone who knows IRIDA before the IRIDA connector is built); which Galaxy reserved variables reach the container environment; how Shiny for Python shares module-level variables across sessions of one process.

**Open points (parked by Eve; all must be decided before the single run, because there is no second pass).**
1. Key renames inside the files: `curated_data` to `cache`, `user_sessions` to `user_data`, `prefer_discovery` to a named choice (for example `data_lookup: by_dataset_id | manifest_paths`), the `features:` block to `flags:`, `show_persona_badge` to `show_app_features_badge`, one `name` instead of `persona_name` and `persona_id`.
2. A launcher with named launch configurations (`./launch dev`, `./launch retest`), the VS Code `launch.json` convention. It sits outside the configuration model.
3. A general operator lock (a block of feature overrides in the deployment file) instead of the one-off `data_ingestion_enabled`.
4. "Agent role" instead of "AI agent persona" for the two agent files.
5. The IRIDA connector assumption above.

**Consequences.**
- A deployment is one file; a Galaxy tool wrapper sets one variable. A developer can start the same deployment with other app features by setting one more variable.
- The words in the UI, the code and the docs mean one thing each; the retired words fail early instead of working silently.
- The rename is large but mechanical: "persona" is in 51 Python files and 87 documentation and rule files, "manifest" in most of the code base. The tests (1215 headless, 37 browser) plus the old-words audit are the safety net.
- Memory notes and the project instruction file that use "persona" or "manifest" are updated in the same run.

**Review decisions (Eve, 2026-11-07).**
- Scope rule: the rename covers the application configuration and what reads, writes or shows it; names of wrapped Python libraries, data content and domain terms, and external tools' own terms (for example the Posit Connect `manifest.json`) are kept. Wrapper libraries are reviewed per file, never replaced blind.
- "Connector" names two things: the adapter library `libs/connector` keeps its name; the deployment-file sense (`connector_path`, `connector_config`, `_load_connector_config`, `connector_template.yaml`, `local_connector`) is renamed to `deployment_*`; `SPARMVET_CONNECTOR` is removed; `docs/workflows/connector.qmd` is split or renamed. It is a fifth retired word in the audit.
- Open points 1 to 4 accepted as proposed: key renames (`curated_data` to `cache`, `user_sessions` to `user_data`, `features:` to `flags:`, `persona_id` to `name` with `persona_name` deleted, `show_persona_badge` to `show_app_features_badge`, `prefer_discovery` to `data_lookup`); the launcher as a later small issue; an `app_features_override:` block in the deployment file instead of the one-off `data_ingestion_enabled`; "agent role" for the two AI agent files. Open point 5 (IRIDA) is issue evezeyl/SPARMVET_VIZ#28.
- Unused or unfinished keys become tasks, not silent deletions: the timed autosave of `user_preferences.qmd` was never built, the saving is event-driven (Apply, leaving Home, assembly), so the key `ghost_save.frequency_minutes` is deleted and the Quarto page corrected (task CONFIG-GHOST-DOC-1); the four `blueprint_agent.*` keys stay, marked "reserved, not implemented" (task CONFIG-AGENT-BACKENDS-1); dead `scripts.*` keys and `get_script_path()` are deleted.
- Stale entries of `.claude/settings.json` are removed (task CONFIG-SETTINGS-CLEAN-1). The history folders `.claude/baselines/` and `.claude/conversations/` are excluded from the audit.
- Design records under `.claude/design/`: live ones are rewritten, history ones get a HISTORICAL banner (the live list is confirmed in the mapping step).

**Gaps found during the review (open, tracked as tasks).**
1. *Recipes location write access.* The deployment guide says the recipes location is read-only for the app, but BLUEPRINT writes component files and branch fragments into it (`blueprint_handlers.py`, around lines 1104 and 1412). The app features and the deployment can therefore be a combination that fails at the first save. Eve's direction (2026-11-07): never overwrite what matters silently. Interim: warn and keep a timestamped backup before overwriting a recipe file. Target design: BLUEPRINT works on a draft copy in the user data location, the manifest validation (issue evezeyl/SPARMVET_VIZ#26) runs on it, and an explicit publish step copies it into the recipes location when it is good. The recipes location can then stay read-only for production and static deployments (CONFIG-RECIPES-WRITE-1).
2. *Application resources are found relative to the working directory.* The app features folder, `config/ui/theme.css`, the sidebars and the development fallback are all read as relative paths (`bootloader.py`, `ui.py`), so a container or an installed copy started from another folder fails. They belong to the code, not to the operator's data, and should be located from the code root, with an explicit setting only if a deployment needs another folder (CONFIG-APP-RESOURCES-1).
3. *Branding is read from the app features file, but belongs to the deployment.* The base stylesheet `config/ui/theme.css` is always loaded and a second stylesheet is layered on top when `theme_css` names another file (`ui.py` lines 18 to 25), which is the intended "default plus optional override" for sites that need their own banner. But `theme_css` and the banner (`get_ui_banner()`, `logo_url`) are read from the app features file, so a static site that needs its own banner would need a copy of a features file; ADR-055 says the deployment overrides it, which the code does not do. Decision (Eve, 2026-11-07): a `branding:` block in the deployment file (`theme_css`, banner title, `logo_url`); the default stylesheet always loads from the code root and the deployment stylesheet only has to hold the differences; the old keys in an app features file stop the app at startup with the migration message. Part of the behaviour phase of the rename (CONFIG-BRANDING-1). The characterization tests of phase 0 already run with the repository as working directory.

**Implementation notes (2026-11-07).**
- Deployment values: `data_lookup` is `data_analysis_recipe_paths` (default) or `by_dataset_id`; `default_data_analysis_recipe` holds the recipe **name** (file name without `.yaml`), not a path; the unused connector method for the default recipe path was removed.
- Names of the old meanings of "recipe": `steps` (the `recipe:` key, `steps_tier1`), `audit_steps` (T3: `t3_audit_steps_by_plot`, `AuditStep`), `example` (gallery: `data_analysis_recipe.yaml`, `example_meta.md`, `example_data.tsv`), `IdTransformation` (libs/id_reconciliation). A name shared between files has one meaning in all of them.
- Old names fail loudly: `app/modules/renamed_keys.py` (launch variables, deployment keys, locations, app features keys, session keys), `libs/utils/src/utils/legacy_keys.py` (recipe file keys, gallery file names). `assets/scripts/migrate_config_vocabulary.py` converts recipes, saved sessions and gallery bundles (dry run by default).
- Two demo deployments (`config/deployment/demo/`) carry the banner and stylesheet the two demo app features used to hold.
- Kept on purpose, with a phrase in the audit: the vendored assets list (`VENDOR_MANIFEST.md`), Posit Connect's `manifest.json`, `AMR_Profile_Joint` and other biology words.
- Not done here (own tasks): the launcher (open point 2), CONFIG-RECIPES-WRITE-1, CONFIG-APP-RESOURCES-1, CONFIG-CACHE-LOCATION-1, CONFIG-AGENT-BACKENDS-1, CONFIG-IRIDA-CHECK-1.



### ADR-091 follow-up: the word "project" (2026-11-07, issue evezeyl/SPARMVET_VIZ#29)

"Project" was the generic word that replaced "species" (Terminology, ADR-003/ADR-029b). Today it was a second name for the data analysis recipe, and IRIDA and Galaxy have their own project, so it is retired for the recipe.

1. `project_id` and related names become `data_analysis_recipe_id`; the text says "data analysis recipe" or "recipe id" where the identifier is meant.
2. The sidebar panel `project_info` (it showed only the deployment name) becomes `data_analysis_recipe_info` ("Info"). It shows the `info:` mapping of the open recipe as written: any keys, nested mappings indented, no fixed field list. `info:` is outside the cache keys.
3. The top-level recipe key `type:` (species, project, pipeline, audit) was read by no code and is removed; `legacy_keys.py` refuses it and the migration script drops it.
4. "Project palette" becomes "Deployment palette"; the app features name `project-independent` becomes `standalone`.
5. Kept: IRIDA's project (`irida.project_id`), `pyproject`, `project_root`, "this project" for the repository.
6. Old names are refused with a "renamed to" message (`renamed_keys.py`); the old-words audit counts "project". Mapping: `.claude/tasks/outdated/project_word_mapping.md`.

Lesson: a panel renderer that reads `active_cfg()` re-renders the whole sidebar (shell stability pattern, ADR-045 R4): the Info content is its own output slot.
