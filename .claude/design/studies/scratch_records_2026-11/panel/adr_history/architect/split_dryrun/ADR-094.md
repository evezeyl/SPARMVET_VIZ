## ADR-094: HOME gates automatically on load (structure + data contract); BLUEPRINT stays manual; runtime failures get a real surface, not a traceback (2026-11-08)

> **Partly stale (2026-11-14, ADR-SYNC-1):** the gate's checks are now the one checker `check_recipe` of `libs/utils` (ADR-100 point 3, DEC03, 2026-11-13); "data vs declared contract" no longer includes `output_fields` (DEC23). The gate itself stays.

**Status:** ACCEPTED and IMPLEMENTED (Eve, 2026-11-08). Authority: @dasharch, decided with @evezeyl.
**Completes:** ADR-087 ("Data analysis recipe errors raise an exception; the app reports and skips, it never exits") — extends its scope from structural load errors to include the data-vs-contract check, and implements what ADR-087 left as "NOT YET IMPLEMENTED". **Begins wiring:** ADR-079 (Runtime Error Discipline) — the renderer side was already fully built and unit-tested; this ADR starts the catch/dispatch side, for the path HOME needs most.

**Context.** Eve: *"Home is the production place — I have a recipe and some data and I want to view and eventually do some refinement. Blueprint is the IDE to create new recipes."* The two spaces need opposite failure behaviour, not the same one tuned differently:

- **BLUEPRINT** — errors are the expected, normal state while building. The existing "Validate" action (BP-VALIDATE-1 / VALIDATE-UI-1, this log, 2026-11-08) is manual and advisory: press it, see what's wrong, fix it, press it again. This is unchanged by this ADR.
- **HOME** — *"we want a system to safeguard the quality of the science behind the app: we want to avoid that a problem with data or recipe go through silently and that the results are not what they ought to be."* A HOME user runs an already-built recipe; they did not write it and may not be able to fix it. The check must be automatic, not a button they have to remember to press, and a failure must never mean "the app crashed" or "the plot rendered anyway, silently wrong."

A real gap made this concrete, not hypothetical: *"the user might not be able to fix it in blueprint because it might not have the possibility (e.g. deployment without blueprint)."* `pipeline-static` and `pipeline-exploration-simple` app features have `blueprint_enabled: false` — a HOME user there has no BLUEPRINT to be pointed at. The rejection message needs someone to contact instead, and until this ADR no deployment had anywhere to declare one.

**Decision.**

1. **HOME's load gate runs automatically, once per recipe, at app startup.** `Bootloader` (the module-level singleton, created once per app process, not per session) runs both `validate_data_analysis_recipe()` (structure) and `validate_data_analysis_recipe_data()` (data vs. declared contract — the same two functions VALIDATE-UI-1 wired into BLUEPRINT's button, same module) against every discovered data analysis recipe. A recipe that fails either check is excluded from `bootloader.available_data_analysis_recipes` — it can never be selected, never becomes the default, never reaches `ConfigManager` through the normal HOME path. It is recorded in a new `bootloader.rejected_data_analysis_recipes` dict (per name: the problem list, the resolved contact) instead.
2. **Never crashes, never silent.** Excluding a recipe is not an error the app reports and halts on — the app keeps running on whatever recipes did pass. HOME's "Data analysis recipe Choice" panel (`home_theater.py`) shows rejected recipes beneath the selector: name, the first two problems, and who to contact. A recipe that fails is simply not an option, with a visible reason — never a silent wrong plot, never a crash.
3. **Contact resolution, two tiers, no fabrication.** `resolve_contact(info, deployment_contact)` (`data_analysis_recipe_validator.py`): the failing recipe's own `info.contact` first, else the deployment's new `branding.contact` field, else nothing shown (never an invented placeholder). `info.contact` already existed as an unenforced convention (`data_analysis_recipe_info.py`, demonstrated in a test since before this ADR); `branding.contact` is new (`config/deployment/templates/deployment_template.yaml`, documented as "strongly recommended for any deployment that hides the recipe selector" — exactly Eve's static-deployment case).
4. **Reading the contact must survive a badly broken recipe.** `read_data_analysis_recipe_header(path)` reads just `id:`/`info:` via a bare `yaml.safe_load` — no `ConfigManager`, no `!include` resolution, no engine involvement — so a recipe whose `data_schemas:`/`wrangling:` is malformed still shows who to contact. Only a YAML syntax error bad enough to break the whole file falls back to the deployment contact alone.
5. **The operator-named default gets the same gate, with sharper error text, not a bypass.** If `default_data_analysis_recipe` / `SPARMVET_DATA_ANALYSIS_RECIPE` names a recipe that exists on disk but fails the gate: with the selector visible, HOME falls through to the first recipe that *does* pass (the user can pick differently) — it never silently opens the broken one. With the selector hidden (the exact case with no escape hatch), this is still fatal at startup, same severity as today's "name not found", but the message now says *what failed and who to contact* instead of suggesting a spelling mistake — because it is not one.
6. **Scope boundary, stated plainly:** if literally every discovered recipe fails the gate, the app still raises at the point a recipe is needed (`get_default_data_analysis_recipe()`, unchanged exception type, improved message) rather than a new graceful empty-state screen. Building that empty state is a real, separate, larger piece of work (`home_theater.py` has no empty-state rendering path today, for this or for the pre-existing "zero recipes exist on disk at all" case) — out of scope here. The common case (some recipes valid, some not) is what this ADR makes safe; the degenerate all-fail case is unchanged from before, not worse.

   exactly as described above (still raises `FileNotFoundError` — some test and call sites
   rely on that). What changed is that nothing in the session-startup path is allowed to call
   it unguarded any more: `Bootloader.get_default_data_analysis_recipe_or_none()` is the new

   empty stand-in (`SimpleNamespace(raw_config={})`) instead of raising when there is no usable

   `bootloader.has_usable_data_analysis_recipe` and renders a short "No data analysis recipes

   `wrangle_studio.render_ui()`/`build_sidebar_ui()`) — no change needed there, consistent with
   point 2 of the "What should happen" framing in the issue (they are where recipes are
   authored). Rescan cadence (the issue's other open question): documented, not changed — the
   `bootloader` singleton still scans once per process at `__init__` time
   (`_discover_data_analysis_recipes`, comment added); picking up a newly added or fixed recipe
   needs a restart, same as any other app features/deployment change today. A few remaining raw
   `get_default_data_analysis_recipe()` call sites stay as they were: they are either reachable

   (`_collect_all_group_plot_ids` returns `[]`) — a real gap only if a feature built for
   "a recipe is open" is used with none open, a materially smaller and different problem than
   "the app won't start."
7. **Pre-release testing is a separate, earlier line of defense, not replaced by this gate.** Eve: a static deployment should ideally catch a bad recipe during deployment testing, before it ever reaches a user. This ADR's gate is the second line — for drift after release (a data file changes shape on disk, a recipe is hand-edited on the server). Neither replaces the other.
8. **ADR-079 wiring begins, scoped to the path HOME needs most.** The renderer side (`libs/utils/src/utils/pipeline_error.py`, `app/src/render/pipeline_error_renderers.py`, `dispatch_pipeline_error()`) was already complete and unit-tested; `PipelineError` was already raised at all 7 production sites; nothing caught it anywhere. This ADR wires the catch point for data materialization (`DataOrchestrator`, the path a recipe that passed the load gate still goes through to actually run) using the `notification` surface. The remaining five retrofit targets (`viz_factory` render failures, T3 Apply, Blueprint inline, Data Import panel, plus the full audit-trail/export/ghost-format capture of ADR-079 Phase 3) are **not** done here — tracked as `PIPELINE-ERROR-WIRE-2` (`tasks.md`), not silently dropped.

**Consequences.**
- `bootloader.__init__` now does real work (two validation passes per recipe) once per app process — measured 2026-11-08: 6 shipped recipes, ≈0.76 s total including Python import time. Acceptable as a one-time startup cost; would need revisiting for a deployment shipping dozens of large recipes.
- `bootloader.available_data_analysis_recipes` changes meaning: "exists on disk" becomes "exists on disk **and** passed the load gate". Anything that iterated it assuming the former (none found at audit time) would need updating.
- `rules_data_analysis_recipe_structure.md §11`'s "Implementation status: target behaviour" banner is corrected — the data-vs-contract half and the HOME-side gate are implemented; the full graceful-degradation promise of ADR-087 (catch *any* `ConfigManager` exit, anywhere, including inside BLUEPRINT's own load path) is **not** fully implemented by this ADR — only the HOME discovery-time gate is. `ConfigManager` itself still calls `exit_if_errors`; BLUEPRINT's own recipe-load path is untouched (correct, per the BLUEPRINT-is-permissive principle above).
- `info.contact` goes from an undocumented convention to a documented, recommended field (`rules_data_analysis_recipe_structure.md §11`).
