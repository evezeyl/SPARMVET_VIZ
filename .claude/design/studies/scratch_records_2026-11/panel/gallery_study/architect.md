## 1. THE LOGIC: is recipe -> check -> index -> filters -> example sound?
The chain is sound in shape: ONE checker (`check_recipe`, profile `gallery`, ADR-100 point 3), one index writer (`rebuild_index`), one listing function, the viewer holds no copy of the terms (`test_gallery_viewer_taxonomy.py`). The shape breaks at three places where a second store exists:

L1. Index vs recipe (the index is a stored copy of what the start check just computed). `sync_index` compares only the key set and `rejected` (`gallery_manager.py:152`). A changed name, taxonomy, path or has_preview is never picked up (reproduced). It touches what the user sees: the filter ticks and the pivot filter on old values; the dropdown shows an old name. A wrong filter result is a silent wrong result (agent_principles 2). DEFECT, fix now.
L2. Picture vs recipe. Nothing ties `preview_plot.png` to its recipe and data (no stamp, GP05 tests existence only). Today true (34 identical, verified); the day a recipe is edited and the picture not, the Gallery shows a plot that is not the recipe's plot, with no sign. DEFECT of the design (a missing proof), fix now, but see 3.8 for the options.
L3. Strip and heading in `example_meta.md` vs the recipe. The strip is shown from the file (`gallery_handlers.py:229-232`), written once, checked only in a test. Equal for 34 today (verified by the MAP and the test). Same class as L1.

Also two stores inside one file: `registry.<id>.taxonomy` and `pivot.by_<axis>` both hold the taxonomy (pivot is derivable from the registry). Nothing reads `registry.taxonomy` at runtime (MAP table), `matching_examples` reads the pivot. They can disagree in a hand-edited or half-written index; the atomic write makes a half-written file impossible, a hand edit is "forbidden" by text only (B9, nothing enforces it). MINE: either drop `registry.taxonomy` or drop `pivot` and compute it in the listing (a few lines); the first is smaller. CONFIRM with ADR-037 (the pivot is the ADR's own word).

And two sources of "what is listed": the index file (names, pivot) and the in-memory `rejected` from the start check; `build_listing` already patches the file with the memory (`gallery_listing.py:40-56`), a sign that the memory is the better source and the file a cache.

## 2. ONE SOURCE: per thing shown
Rule I propose, one sentence: what the user sees about an example is read or derived from the recipe plus its two content files (data, guidance text); everything stored is a cache that the start check compares in full and rewrites, and the one thing that cannot be derived at start (the picture) carries a stamp of the inputs it was drawn from.

If `label_keys.info` (spec line 13, PENDING Eve) changes later, the Gallery does not move. `info.label` stays required by I01 for every recipe (common checker); in a gallery recipe it is the recipe maker's label (her words: "info is more for the recipe maker"). ## 3. THE RECIPE RULES THE GALLERY LACKS (part d)

3.1 Where the list of allowed taxonomy values lives. CLEAR in the spec, AMBIGUOUS in the rules.
- Spec: `recipe_format_spec.md:577` D3 "The specification is also a data file ... the vocabularies (... the gallery terms with label, icon, order and a line of meaning) ... The checker, the filter panels, the index order, the cheat sheet ... read it or are generated from it." DECIDED (D-0039, DEC47, ADR-100 point 9).
- Rule: `rules_gallery_standards.md:37` "TAXONOMY_CHEATSHEET.md - single source of truth ... add them to the cheatsheet first". ADR-063:1975 "single-file canonical reference". These two say the opposite of D3. Verified: no code reads the cheatsheet; the checker and the filter panels read `recipe_spec.yaml:187-215`; adding a value to the cheatsheet changes nothing.
- Recommendation (MINE): the ONE source is `recipe_spec.yaml` key `gallery` (it is the data file the checker already reads; the rule "one checker, one spec"). The cheatsheet becomes a generated document: the spec gets the "line of meaning" D3 already promises (terms as `{term, meaning}`; today the meanings exist only in the cheatsheet, so they must move into the spec first, otherwise generation loses text), a script writes `TAXONOMY_CHEATSHEET.md` from it, and a test fails when the file differs from the generated text (the same pattern as the strip test). The rule file is changed with Eve's double confirmation (spec section 9 "Order").
- Alternative (smaller, weaker): keep the cheatsheet handwritten and add a test that its term sets equal the spec. That is two stores guarded by a test; it works (I verified they are equal today) but is the "half fix" shape the principles warn against: the value still has to be typed twice.
- Format-version note: spec line 187 "open; a new term does not change format_version". A new term is a spec-file edit plus regenerated cheatsheet plus (if a filter label changes) nothing else. Removing or renaming a term DOES break shipped recipes: the checker refuses (GP03), so the example is left out. That is correct and shown (rejected block), but it deserves a line in the rule: removing a term is a breaking change (rename table needed).
