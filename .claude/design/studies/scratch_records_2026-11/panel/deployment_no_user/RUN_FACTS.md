## How the scratch world was built (repeatable)
All under `tmpAI/panel/deployment_no_user/run_scratch/` (main tree). Scripts in `bin/`, screenshots in `shots/`, app console logs in `logs/`.
- `bin/build_world.sh <name>` makes `<name>/` with: `raw_data/` = copies of `assets/test_data/duplicated_1_test_data_ST22_dummy/*.tsv` (files named after the tables), `recipes/` = copies of `1_test_data_ST22_dummy.yaml` and its folder `1_test_data_ST22_dummy/`, empty `user/`, `cache/`, `gallery/`, and `deployment.yaml` (modelled on `pipeline_test.yaml`: `deployment_type: filesystem`, `data_lookup: by_dataset_id`, `default_data_analysis_recipe: 1_test_data_ST22_dummy`, the five locations as ABSOLUTE paths into the world).
- I used `by_dataset_id` (not `data_analysis_recipe_paths`) because the demo recipe's `source.path` points into the repository's own `assets/test_data/`; with `by_dataset_id` every data file read is my copy (RUN: the app log shows the stored tables written under `<world>/user/anchors/`).
- `bin/startapp.sh <world> <port> [VAR=val]`: `PYTHONPATH=. SPARMVET_DEPLOYMENT=<world>/deployment.yaml SPARMVET_APP_FEATURES=pipeline-static ./.venv/bin/shiny run app/src/main.py --port <port>`. Ports used: 8741, 8742 only. Every app was stopped by its PID at the end (RUN: no `shiny run` process and no listener on 8741 to 8745 remain). Rights restored (`chmod -R u+w`).
- Browser: headless Chromium by Playwright, 1920x1080; `bin/visit.py`, `bin/case5.py` (cases 5 and 6), `bin/recover.py`, `bin/case7.py`, `bin/two_visitors.py`, `bin/export.py`.
- The "weekly refresh" is a file written next to the data file and moved over it (`os.replace`, atomic). The "half written" files are written in place (as a copy in progress would be).
- Load before every run was read; it was 2.7 to 10.7 (limit 10 respected at start of each run; slow first openings of 22 to 31 s were measured under load 3 to 10).

## What a static page needs today to work (RUN unless marked)
- A user folder that the app can create and write: without it the visitor gets a blank grey page with no text (cases 2a, 3), although the page only shows data. The need comes from the sessions folder made for every browser connection (READ `server.py:149`), not from anything the page shows.
- Even with `session_management` and `ghost_save` off, the page writes a session record (`assembly.json`) and 24 stored tables at the first visit.
- Read access to the recipe folder and the data files, with the table names as file names (here `by_dataset_id`).
- A recipe that passes the start check with the data present: otherwise the process exits at start with a console text and there is no page (case 8; D-0427).
- About 22 to 31 s for the first visitor after a start or after a data change (the tables are built at that moment); 2 to 4 s afterwards.
- Each data refresh needs the visitor to reload the page (F5), or a new visit, to see it: a page already open keeps the old picture (case 5). The stored tables are rebuilt at the first opening after the change, only those that depend on the changed file.
- For the export: a writable temporary place; the folder is taken from `TMPDIR` (case 10). Without it, no rendered report.
- For a pipeline that supervises the process: a start failure is an exited process with text on the console (case 8).

## What a visitor is not told (RUN unless marked)
- With an unusable user folder: nothing at all, a blank page (2a, 3). With stored tables already there: server paths and a Python error text (2b).
- That the data file changed while the page is open, unless he clicks another plot tab; the notice then comes once, as a toast that disappears, and the open plot stays the old one (5, 6). Not tested: whether the notice also arrives after the visitor does something else than a tab click.
- Which data or which date is shown: no date, no hash, no file name or time anywhere (5d).
- That the data file is only half written: the page shows a table of half the samples as if it were right (7a). This changes a result silently. A cut inside a character is refused with a reason (7b), a cut at a clean place of a line is not.
- That the cause of a "No data analysis recipes yet" page is a changed or damaged data file: the text speaks of the recipe ("Correct original_name") and gives a contact (6, 7b); the file's current headers are only in the console.
- That the page recovers by itself when the good file is back (6r): it does, within 5 s, with a notice, but the refused page does not say so beyond "HOME tries it again when one of its files changes".
- Why the export has no rendered report when the temporary folder is unwritable: the suggestion says "install Quarto" (10).
- That another visitor exists and shares the session record: there is one record for all visitors (4).
