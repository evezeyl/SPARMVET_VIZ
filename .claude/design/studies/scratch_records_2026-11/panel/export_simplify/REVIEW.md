## Findings by severity

### F1 (must fix): in the instant after a recipe switch, Export is active and exports the NEW recipe with the OLD recipe's field values
- Ran (`p3_race.py`, 20 switches A to B to A, each followed at once by a press on Export, the page's own click event): 20 of 20 presses were accepted (button not grey), 0 of 20 lost, 0 of 20 left the button stuck grey. 19 of 20 bundles held the plots of the recipe just chosen with the field values of the recipe left (for example recipe B, 3 plots, `Preset: publication (DPI=600, 9.0x6.0 in)`, png: those are A's values; B's own are web, SVG, 8x5). 1 of 20 (press 13) held the recipe left, with its own values (the press reached the server before the switch).
- Why (read): the key of the session changes in `_sync_session_provenance`; the new fields are sent after that (`_show_the_fields_of_the_session`, `export_handlers.py:786-808`). Until the page applies them the button is active, the panel shows the old recipe's values, the server holds the same values, so the echo of D-0270 agrees with the screen. `export_ready.js` only greys at a change of an Export field.
- Window (ran, `p3g_window.py`): 154 to 343 ms from the switch to the push on the 6 shipped recipes (2_test 159, stress_test_master 173, figshare 343, demo_abromics 205, 1_Abromics 183, 3_test_no_joins 154). By hand a user is slower than that on a small recipe; a recipe whose data hash takes longer makes the window longer (not measured: no large recipe on this machine).
- What the user sees: nothing wrong on the screen (the old values), the bundle README names the values used, so nothing is hidden, but D-0288 and D-0289 ("the functionality follows the recipe that is active") and the aim of D-0270 ("the button is greyed from each change ... until the server confirms") are not kept in this window.
- Named fix: the page greys the button at the recipe switch (the selector `data_analysis_recipe_id` changes) and the server opens it only after the fields of the new session were applied and echoed; or the page and the server carry the session key together with the fields (see F2). A test: a press 10 ms after a switch is refused; the bundle after the wait holds the new recipe's own values.

### F2 (fix with F1, same mechanism): two recipe switches A, B, A within about 30 ms overwrite A's remembered choices with B's, silently
- Ran (`p3c_quick.py`, `p3d_quick.py`; A had publication, png, 9x6 before each switch pair): gap between the two switches 3500, 1500, 700, 300 and 100 ms: A kept its values (5 of 5); 60 ms: kept (1 of 1). Gap 30 ms: A shows B's values (web, svg, 8x5) and A's store holds them afterwards (after a normal B then A round trip A still shows web/svg/8x5): A's choices are lost for good (1 of 1). Gap 0 ms (the two selections back to back): the same (1 of 1 with the right starting values; two more runs of 10 ms and 0 ms started from the already-lost values and show the same state, not counted). The button was not grey and the selector said A.
- Why (read, reasoned): the server sees A's inputs still equal to A's wanted values when the second switch arrives (the page has not yet echoed the push for B), so it sends no push for A; then the page's echo of B's values arrives and `_remember` (`export_handlers.py:754-777`) stores it under the key that is now A (the key is read isolated at that moment). A write is not tied to the key the page was showing.
- Likelihood: a mouse or keyboard cannot do two selector changes in 30 ms; a slow server (the second change sent before the first flush ends) widens the window (reasoned, not run). The consequence is a silent loss of the user's choices of one recipe and B's values shown on A (D-0050). Same fix: the page reports with each field the session key it shows, or the server ignores the echo of a push.
- Related, ran (`p3f_user.py`): a user change made 0 and 40 ms after a switch to a field that the push also sets (plot format) is overwritten by the push (the field flips back about 130 to 170 ms later, visible, A not touched); from 100 ms on the user's change wins and is kept (3 of 3). A change to a field the push does not alter wins at 0, 40, 100, 160 and 250 ms (5 of 5). So no unseen loss there.
