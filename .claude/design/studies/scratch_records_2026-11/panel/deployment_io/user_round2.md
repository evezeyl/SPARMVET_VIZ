# Deployment study, round 2: user and deployer viewpoint (panel-user, 2026-11-21; filed by the coordinator from its report; it read the three other texts in full; no code read, nothing seen in a browser)

1. **Same name in two places.** One rule: refuse, and name both places. If the two files are identical, show one entry labelled "Shared and Mine". CHANGED ITS MIND (first round: let the user pick): a user who picks cannot tell which file the methods section describes. The owner's case works: a consortium recipe copied and changed gets a new date under `name_date`, so it is a different name; both show with their place label. Only a same-day copy collides. The refusal must give a way out: "Two recipes are named amr_2026-11-17: one in Shared recipes, one in My recipes. Their content differs. Neither is opened. Rename or remove the one in My recipes, then reload." No deployment-file setting for this rule: a setting that changes which file a figure uses is a silent change per deployment.

2. **Nothing writable.** (a) stop at start: the page cannot be used and the person at the screen cannot fix it. (b) temporary folder for the session: the page works; risk that the user believes something is kept, and a system temp folder may be readable by others. (c) the deployment file chooses: a declared intent, visible and recorded. Supports (c) with (a) as the default: unwritable with no declaration stops at start; unwritable with the declaration runs with the banner "Nothing is saved on this installation. Your session ends when you close the page. Download to keep a result." Cost: (c) needs (b) built.

3. **Access words.** In the file: `read | add | replace` per place; one deployment-level statement `users: one | many`; one `persistence: none` when nothing is saved. Mapping to the screen: `read` = "Shared recipes (you cannot change these)"; `add` = "Shared recipes (you can add, not replace)"; `replace` with `users: one` = "My recipes"; `replace` with `users: many` = "Saved in this app (everyone who uses this app sees them)"; `persistence: none` = "This session only". The label comes from the app; the deployer cannot write "My" by hand.

4. **Private data.** One flag, `private: true` on a data place, allowed only with `users: one` (refused at start with `users: many`). It must prevent: stored tables built from private data going into a shared place; a write from a private place into a shared one; a reproducibility export taking private data files unseen (the export dialog lists them: "These files come from your private place and will be in the download: tick to include."); a session record keeping a server path (it records the place name). That is the least that makes the owner's case safe.

5. **Confinement.** Refuse a `source.path` outside the declared places, and a Data Import write outside them. The shipped recipes that point into `assets/test_data/` move to a declared "examples" read place named in the shipped deployment files (scripted with the migration). The refusal names the path and the missing place.

6. **Migration.** Step 1: a start check on the five existing keys (create `user_data` at start, fail with a plain message naming the place). Step 2: the `name_date` module and a sorted recipe list. Step 3, one atomic pass: the `places` block, the scripted migration of the seven shipped files, refusal of the old keys, with the refusal and error messages inside the same step. No alias. Screens after step 3.

7. **API and connectors.** "Pull into a local read place, then read" covers the pipeline job folder and an API, if the pull happens at start and the bytes are kept. To record per file from an API: source identity (host, project, dataset), date and time fetched, version if given, content hash, and the kept copy of the bytes. Screen: "Given by <source> on <date>. It cannot be saved here." If the pull fails the app stops at start and names the source; it never falls back to another place.

8. **D-0340.** Sentence for the owner: "D-0340 is respected: the audit folder gets no variable of its own and stays inside the session folder of the user's place. The new `places` block replaces the five location keys; it is the only new configuration, and the owner is asked to confirm that this is not what D-0340 meant by a new variable."

9. **Objections.** To the data scientist's setting `resolution: {same_name_in_two_places: refuse_unless_identical}` (a setting is the wrong place). To the architect's "Container with nothing writable: start refuses": it leaves a deployer who is not a developer with an unusable page. `required: false` must show its notice in the selector and at opening. A write probe only on places declared `add` or `replace`, never in a `read` consortium folder. Removal "by hand" in an `add` place cannot be done by a normal user on a shared server.

**Still open between us:** whether the temporary mode (b) is built at all; the Data Import overwrite (keeping the old file needs a folder and a naming rule); whether real users understand "locked" and "shared"; who may remove a same-day file from an `add` place without an identity; `users: one | many` is a statement the app cannot check.
