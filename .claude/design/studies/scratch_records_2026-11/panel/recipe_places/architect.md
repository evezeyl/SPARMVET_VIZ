## 0. Flags first
1. **The default recipe depends on the file system.** `_discover_data_analysis_recipes` is `glob("*.yaml")` unsorted (bootloader.py:416-417) and the default is `list(available.keys())[0]` (:656). VERIFIED by run: with five recipes the default was `x_2026-11-17`, not `1_test_data_ST22_dummy`. Same files, other machine, other default. This breaks "the same data and recipe give the same result" at the first screen. Fix (sort) is small and independent of every model.
2. **Two stores that disagree today.** HOME reads the deployment's recipes location (`bootloader.get_location`, bootloader.py:185). BLUEPRINT lists and writes the hard-coded `config/data_analysis_recipes/pipelines` (blueprint_handlers.py:975, :2666, :2711). They are the same folder only in the dev deployment. On any other deployment BLUEPRINT edits a folder HOME does not read. VERIFIED by reading.
3. **D-0184 (check a recipe when selected, not all at start) is not built.** The gate still runs on every discovered recipe at start (bootloader.py:187-191). Every older version kept in a folder adds a start-up check until D-0184 is built. CONFIRM with Eve whether it is still wanted.
4. **"Specific users may modify common recipes" cannot be enforced by the app without an identity.** No identity, no `os.access`, no user header anywhere (grep over `app` and `libs`: none). Any rule the app can apply (an app features flag, a write test on the folder) tells apart DEPLOYMENTS (processes), not people. On one shared server with one process everybody has the same rights. So "specific users" means, today, "specific running apps": an author app (writes) and a reader app (reads) on the same recipes folder. This must be told to Eve plainly.
5. **"Own directory" is shared on a shared server.** `user_data` is one folder per deployment (ADR-091, FACTS). An overwrite control "only in the user's own directory" (D-0394) is only really own where the deployment gives one user (local PC, a Galaxy or IRIDA job, one app per user). On a shared server it must be shown as "shared by all users of this app".
6. **A dated copy is not self-contained for four shipped recipes.** `1_Abromics_general_pipeline`, `3_test_no_joins`, `demo_abromics` include fragments from `1_test_data_ST22_dummy/` (and `..`) (grep, VERIFIED). A dated final save that only copies the recipe and its own mirrored folder would keep pointing at another recipe's mutable folder: the "frozen" version changes when the demo folder changes (silent). In a place without a `pyproject.toml` above it an `!include` outside the recipe's folder is refused (T11, `config_loader.py:44-80`, `test_an_include_outside_the_project_is_t11`, ran: passes). So any copy (to own place, final save) must copy every file the recipe read (`loaded.files`, or `Bootloader._recipe_files`) into its own mirrored folder and rewrite the includes. One function, used by the final save, the copy-to-own action and the audit recipe (D-0332 "copying the recipe's files"): one authoritative way, not three.

## 2. "Newest per name" (ran, `newest.py`)
Rule: `^(?P<name>.+)_(?P<date>\d{4}-\d{2}-\d{2})$` anchored at the END, date checked with `date.fromisoformat`; anything else is an undated name (the whole stem).
- `1_test_data_ST22_dummy` -> undated, name = itself. `amr_2026-11-17` -> (amr, 2026-11-17). `amr_v2_2026-11-17` -> (amr_v2, ...): `amr` and `amr_v2` are two different names, never merged. Digits or underscores inside the name are harmless because only the tail is read. `a_2026-11-17_2026-11-18` -> name `a_2026-11-17`. `run_20261117`, `amr_2026-13-45` (not a date) and `demo_imported_20261117T101500` (the bundle import's name) -> undated, so the import does NOT follow the rule (flag for her: either the import takes a dated name or it is told as "outside the rule").
- Sorting: a plain text sort of whole stems puts the oldest first; reversing it also reverses the names. D-0391 "sort from most recent to oldest by name" needs two keys: name ascending, date descending. A plain sort only happens to group names while digits sort before letters; do not rely on it.
- Same name, dated and undated (`amr` and `amr_2026-11-17`): the undated one is the oldest in my key. OPEN: or refuse the mix.
- Two files of the same name and the same day cannot exist (D-0390: refused). A same-day correction needs deleting the first by hand: in the common place the app user cannot delete (see flag 4), so it goes to the operator. State it.
- Pure function, testable without a browser: `split_name_date`, `newest_per_name`, `sort_for_selector`.

## 3. The models
Common reading: "common" = the deployment's `data_analysis_recipes` location (ADR-048 Location 2, ADR-091). "Own" = a folder `<user_data>/recipes/` (a subfolder of Location 4, no new location, no new configuration variable: same line as D-0340). I read M3 as "the app writes only in the user's place and reads the common one only if the operator mounts it there".

### M1 One common place read-only, own place in `user_data/recipes/`
- Reads: common, then own; both discovered, one list, each entry marked "common" or "mine". Writes: only own. BLUEPRINT opens a common recipe read-only and offers "copy to my place" (dated name, copy of all files, flag 6).
- Same id in both: REFUSED at discovery, both marked with a plain line (the app does not choose which wins). The copy action therefore gets a new date, so it cannot collide.
- Name rule: own place: no date required for a draft; the typed name is kept; a typo edit replaces (the overwrite control, D-0394). Common: filled by the operator outside the app. "Export for production" is a download (zip), the operator puts it in common.
- Who may write: by the OS for the common folder (app process not allowed) and by the app only in own. No identity needed. Where it fails: a shared server shows one own folder to all (flag 5).
- Platforms: local PC fine; Galaxy and IRIDA: per-job file systems are assumed (EXTERNAL-UNCHECKED), so own recipes must be downloaded to survive; server: shared own place.
- Pros: nothing is written into the common place by the app; consistent with the docs (recipes read-only, deployment_guide.qmd); easiest to test. Cons: the production step is outside the app (her "enforce the dated final save" is not enforced, only recommended); two places in HOME.
- Touches: ADR-091 gap 1 (partly implements it), ADR-048 (a subfolder, five locations stay), ADR-092 (id == stem holds in both places), ADR-094 (a new own file needs a rediscovery, see step 4).

### M2 ADR-091 target: drafts in own place, "export for production" writes the dated file into common
- As M1 plus one write path into common: publish = MOVE `name` from own to common as `name_<today>`, after checks (name free in common, all files copied and self-contained, hash of the destination = hash of the source), then delete the own copy. A move, not a copy, because the same id in both places would be refused (M1 rule) and because two copies can disagree. The id changes at the move (`amr` -> `amr_2026-11-20`) so a session saved on the draft is refused on the dated recipe (D-0317), told in one line before the move.
- The rule is enforced where she asked: at publish. Undated demos and templates are not touched (b below).
- Who may publish: an app features flag (one kind of user per running app, ADR-091 "describes a type of user") AND the folder is writable (a write test at start, to tell the user honestly when the flag says yes and the folder says no). Specific USERS only through two apps (flag 4). A later identity connector (ADR-091) could narrow it; nothing to build now.
- Typo edit: in own place a replace (control). In common: no replace; a typo means a new dated file, or the operator.
- Point of no return: the delete of the draft after the move; what checks it is the hash comparison before it, and a refusal when the destination exists. Not caught by an audit: a hand edit of the common file after the move; a crash between copy and delete leaves the same id in both places, which the discovery refuses with a plain line (a safe failure, not silent).
- Pros: enforces her working direction; matches the ADR-091 target; the app informs, the user publishes. Cons: the largest build; it writes into the common place, which the docs call read-only (the doc must change); needs rediscovery without restart; the "old versions" move is also a write into common.
- Touches: ADR-094 (a restart for new recipes: reconsidered, see step 4), D-0184 (see flag 3), ADR-091 gap 1.

### M3 Everything in the user's place; the common place only filled by an operator
- The app reads and writes one folder, the user's (per-user in a local PC, a Galaxy or IRIDA job, or one app per user); the operator puts common recipes there or mounts them read-only. No two-place logic in the app; BLUEPRINT just takes `get_location` instead of the hard-coded path. The dated name is enforced at the "export for production" download. Overwrite everywhere in that folder.
- Pros: smallest change (fixes flag 2, nothing else); same code path as today. Cons: on a shared server the "own" place is the common place, so the overwrite control would be given to everyone (against D-0394) unless the deployment gives each user a folder; so M3 is only sound where there is one user per app. It silently relies on the deployment; the app cannot tell the user which kind it runs in.

## 4. Recommendation (one combination)
M1 first, M2 as its second part; M3 is only a special case (one user per app, own = common) that M1 covers when own and common are given the same folder (the discovery refuses the identical-folder case: treat as one place). Because what Eve wants (an enforced final save, a typo edit in the user's own place) is M2, and ADR-091 already names it. Open for her: the choices in section 7.

## 6. Order so every step leaves a working app (each step own tests; none changes behaviour on a one-folder deployment)
1. Pure module of names (split, newest per name, two-key sort) + tests: edge cases above, a failing case on purpose. Not wired.
2. Sort discovery and default (flag 1). Test: two runs with different file-system order give the same default.
3. `recipe_path(id)` resolver replaces the 13 sites; an architecture test (grep-like) forbids the pattern elsewhere; same behaviour.
4. Places and discovery of two folders, collision refusal; own place absent = unchanged. A `rediscover()` method called at known events only (not a poll). Test with two `tmp_path` folders, no browser.
5. BLUEPRINT reads the deployment's places (fixes flag 2); writes only where the place is writable; refusal text when a place is read-only.
6. Selector: place marks, newest per name by default, "show older versions" switch; sessions keep working because the gate and resolver know every version, only the selector hides them.
7. The shared copy function (self-contained files, hash check, includes rewritten) with tests on the four recipes of flag 6 and on a place without `pyproject.toml`.
8. Own-place overwrite control (typo edit), gated by place and flag.
9. Publish (move) with the checks and the plain screens; moving older versions to `old/` only if she wants it by the app (it is a write into common; by hand is simpler).
Each of 1-3 is independent and safe; 4-6 deliver M1; 7-9 add M2.

## 7. Her points b, d, and what to tell her
- **b (scope).** Leaving the demo, the templates and the Gallery examples undated breaks nothing, VERIFIED by reading: the id == stem check has no date rule, the gate and tests key on stems, 8+4+5+1 shipped files and 35 Gallery bundles (ids = folder names) never pass through a "publish". The rule lives in the ACTIONS (publish, upload to common), not in discovery, so nothing needs to "know" a production recipe from a demo one: no `info.category` is usable (free text: "Edited", "Regression Test"...). Tests keep their fixed names (`test_there_are_pipelines_to_check` counts 7 pipelines; renaming would break it, so do not rename). Only the bundle import's `_imported_<timestamp>` name does not follow the rule: she decides.
- **d (final save).** "A dated new file at the final save, a replace for a typo edit" is coherent with "an upload under an existing name is refused" (D-0390): the typo replace is a different action in a different place (own); a dated publish never replaces. With D-0362: a replace keeps the id with other content: the session is refused (or, if she keeps B, only when what the recipe does changed: open; the byte hash would refuse after a comment edit). A dated publish changes the id, so sessions on the draft are refused as "another recipe" (D-0317). The upload handler (ingestion_handlers.py:38-54) is unused on screen; if built, it copies with no existence check = silent replace today, so it must be refused-by-default first.
- **Not verified here (to check on the real platforms):** Posit Connect and Galaxy: is the app's recipes folder writable; does `user_data` persist between runs and per user; is a user identity header available to the app (ADR-091: "a connector task for later"). Platform behaviour I stated is EXTERNAL-UNCHECKED.
- **Tell her to choose well:** (1) on one shared server the app cannot tell users apart; "specific users" means a separate author app; (2) the "own" folder is shared on a shared server; (3) the same name in both places is refused, not resolved; (4) publish is a move and changes the id (old drafts' sessions are refused); (5) the app cannot enforce dated names for files put in by hand; (6) the demo stays undated and nothing breaks; (7) what "modified" means for a session remains open (D-0393).
- **What an audit or test would not catch:** a hand edit of a file after publish; a dated recipe that includes another recipe's folder (only the self-containment test); a shared server where own is shared; a platform where the folder is writable only in some runs.
