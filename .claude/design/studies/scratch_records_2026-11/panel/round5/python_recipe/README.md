# Q7: a recipe as restricted Python, and back (architect viewpoint; scratch only, no repository file edited)

Evidence classes: RUN (executed here), READ (file:line), REASONED. Interpreter `./.venv/bin/python`, Polars 1.40.1, plotnine 0.15.4.
Everything here is scratch. `run_all.sh` re-runs every comparison and writes `results.txt`.

## Flags first: where the Python file and the recipe can disagree silently
1. **Theme (RUN).** Plain plotnine draws `theme_gray` when no theme is written; the app adds `theme_bw`. The same code gives two pictures. The reader refuses a plot with no theme.
2. **Jitter seed (RUN; ADR-090 point 2 knows it).** `geom_jitter(random_state=0)` in plotnine means "no seed": two runs give two pictures. The file must say `np.random.RandomState(0)`. The reader refuses a bare number. Whether seed 0 is written back into the recipe depends on the open Q1 (seed written or default).
3. **The picture is more than the layers (RUN).** The app adds axis-text size and rotation from the data (L3 "optimisation"), a default theme, a position set on the previous layer, labels after the layers. Without the L3 lines 3 of 3 figshare pictures differed. The file carries them as lines tagged `[AUTO]`, `[DEFAULT]`, `[POSITION]`; they are frozen to the data of the run.
4. **Found by writing the second reading from the spec, not from the engine code (RUN).**
   - Known, DEC16 / #77: a schema plotted directly ignores its own `tier2`. In `1_test_data_ST22_dummy`, `ResFinder` has two tier-2 steps and `amr_heatmap` plots it: the Python file (spec reading) adds `total_gene_count` and sorts, the engine does not. 1 table and 1 picture differ; every other table and picture is identical. With the engine mirrored (`SPEC_READING=0`) they match: so a test written from the engine's code would pass with the bug in both.
   - **New, not in the tracker as far as I grepped**: in `virulence_bar` the recipe says `theme_minimal`, then `theme_legend_position`. The factory's de-duplication (`plot_config_resolver.py:87-132`, key `("theme", None)` for every name starting `theme_`) drops `theme_minimal` and the default `theme_bw`; the picture is grey (`png/1_test_data_ST22_dummy.virulence_bar.engine.png`). A bug of the factory, found because the generated Python had no theme line.
5. **Plain Polars versus the engine (RUN).** `cast` 2022.9 to Int64: Polars gives 2022, the engine stops. Join keys Int32 against Int64: Polars joins, the engine refuses (ADR-102); String/Int, Int/Float, Categorical/String: Polars refuses too. These are loud differences.
6. **What the comparison cannot see (RUN).** On `2_test_data_ST22_dummy` three of six mutated files were NOT caught: inner join to left join, threshold 90 to 91, select without `cs.all() &`: the data has no unmatched sample, no identity between 90 and 91, and declared order equals file order. A join without `maintain_order` is also not caught on 70 rows. "Equal to the engine" proves what the data exercises. Caught: dropped sort, Categorical to String.
7. **Hashes (RUN).** After the round trip the tier-1 key and the file-set hash differ even though the result is identical: the YAML writes `original_name` equal to the slug (6 times here), the Python cannot. The cache rebuilds; the provenance hash is another one.
8. **Not carried by Python at all (READ).** YAML comments (the loader drops them: `# EDIT HERE`), the fragment split of `!include`, the checker advices J12/J13, the tier-1 parquet store and its key (ADR-089), the data lookup rule (`data_lookup`: a path baked in the file vs production lookup by dataset id), the palette *name* (colours come from the app's palette file), `plot_defaults.default_font_family` (read by Blueprint and the checker, used by no drawing code: READ + grep).

## 1. Recipe to Python: results
RUN on the 7 shipped pipelines plus `retest_top_n_other`: **77 tables compared (ingredients after tier 1, tier 1, tier 2), 76 identical** in rows, order, column order and dtype (Categorical level order too); **29 pictures, 28 byte-identical** PNG. The two differences are item 4 (known #77). Tier 1 through the parquet store changed no dtype or order on these recipes.

Registry (RUN, `classification.txt`): 68 actions. A: 50 plain calls (the engine's own equality tests, `test_polars_actions_equal_polars.py`, prove them against direct Polars). B: 3 need explanation or inline code (`modif_filter`: a plain `.filter(...)`, with `| pl.col(c).is_null()` for `na: keep`, 26 cases equal; `polars_join_where`: the engine sorts the pairs by row index, Polars gives no order, READ `polars_time_joins.py:274-297`, not written in the prototype; `step_top_n_other`: about ten Polars lines, written out inline, identical on its retest). C: 12 plain calls where the engine only refuses more (cast, join, join_asof, rolling, group_by_dynamic, rank, remove, top_k, bottom_k, std, var, quantile). D: 3 eager (`pivot`, `sample`, `describe`: `.collect().m(...).lazy()`). `polars_with_columns`, `polars_group_by`, `polars_remove` carry formula text: that text *is* Python (FORMULA-SAFETY-1); the file holds it verbatim.
191 components: 125 exact; 44 modified: 13 theme layers (`base_size`/`base_family` to the theme, other keys to `theme(...)`), 8 `position_*` (a layer after the geom in the recipe, an argument of the geom in plotnine), `breaks_integer` (needs the project helper `_integer_breaks`: a `def`/import the subset must allow by name), list-to-tuple conversions, the seeded jitter; 22 own (custom themes, `facet_rows`..., `guide_*`, viridis wrappers, `theme_custom`). Each of the 66 needs its own two-way rule. In the prototype: 17 components, all pictures identical.

Input is the largest block that is not "one call": the declared fields become `scan_csv(..., infer_schema=False).select(cs.all() & cs.by_name(...)).rename(...).with_columns(strip, missing words, cast)`; the engine's check that names the offending values becomes a strict cast that stops without naming them. `cs.by_name(a, b)` returns the ARGUMENT order, `cs.all() & cs.by_name(...)` the file order (RUN): the engine keeps file order. A `when/then(None)` without `.alias` is named `literal` and fails on two fields (hit in the prototype).
What a Python reader must be told: the NA choice (`# [NA] remove|keep`, Polars' own default is remove), the order rules (arguments `maintain_order`, visible), the seed (visible), the join key rules and advices (not visible), includes (flattened), the tier-1 store (absent), the data path (baked in), descriptions and labels (23 to 36 % of the recipe values: `#   key: json` lines, 15 to 28 % of the lines of the file).

## 2. Python to recipe: the subset, the keywords, what is refused
Allowed (read by syntax tree; nothing is run): imports `polars as pl`, `polars.selectors as cs`, `numpy as np`, `from plotnine import ...`, one project helper by name; assignments `name = <chain>` each name once; the final `DATA = {...}` and `PLOTS = {...}`; calls with literal arguments (number, text, True/False/None, list, dict); formulas as expressions checked by `formula_problems`; `pl.<Type>` for types; `np.random.RandomState(<int>)` for seeds.
Keywords (comments): `# [RECIPE]`, `# [INPUT] id`, `# [TIER1] id`, `# [TIER2] id`, `# [JOIN] id ingredients=[...]`, `# [GROUP] id`, `# [PLOT] id group= target=`, `# [OUTPUT]`; a step note `# [NA] ... | comment: "text"`; plot tags `[DEFAULT] [AUTO] [PLOT-DEFAULT] [SPEC-THEME] [FACET-BY mapping|spec] [SPEC-TITLE] [LABELS] [POSITION] [SEED] [MODIFIED] [OWN] [RECIPE-ELEMENT-TEXT]`; `#   key: json` lines carry labels, descriptions, taxonomy. Ids with a space are quoted (a shipped group is called "AMR Integration").
Refused, with line and fix (`refusals.out`): lambda and `map_elements`; `for`, `if`, `def`, `with`, bare calls (`print`); a name assigned twice; `&` inside a filter (write one filter per condition); `str.contains` or `is_null` in a filter (use `drop_nulls` or `remove`); `select` with expressions; `sort`/`unique`/`join`/`sample` without the required arguments (the checker's own messages, e.g. "maintain_order is required by polars_sort"); `on='a'` (the recipe takes a list); an unnamed `agg`; two expressions in one `with_columns`; `.collect()`, `.pipe()`; `pl.read_csv`; a join with a table that is not an input; f-strings and variables as arguments; a formula that runs code; a bare `theme(...)`; `random_state=0`; positional `aes('b','a')` (my first reader READ it and silently lost x and y: found by the refusal test, fixed); no theme. A call with no action (`melt`) lists the actions that exist. Not read at all: anything the file does through variables, loops, helper functions, reused names, calls inside calls other than formulas.
The round trip (RUN): **6 of 7 recipes come back identical as data** (after two harmless normalisations: `original_name` equal to the slug, `tier1: null` against `[]`); the 7th differs by one layer, the `theme_minimal` the factory had dropped (item 4). The engine on the re-read recipes gives the same 74 tables and the same 28 pictures (the retest recipe is not in the round trip). Formulas come back byte for byte (the reader keeps the source text, not `ast.unparse`).

## 3. Options
| | Pros | Cons | Touches |
|---|---|---|---|
| **A. Recipe to Python only: generated read-only check file in the export** | a Polars/plotnine user checks by running; a second reading of the spec that found two engine bugs in one session (RUN); no second source of truth if marked derived; effort small and bounded | does not write recipes faster; the file is frozen to the data of the run (AUTO lines); 66 plot components and 3 actions need own rules; a plot is a rendering of the cascade, not of the recipe | ADR-104 point 2 (recipe is the document: unchanged if the file is derived and never read back); ADR-090 (seed visible); ADR-106 V1/V2 (the `exact/modified/own` field is the table the generator needs) |
| **B. Both directions** | faster writing for Polars users | the file becomes a second serialisation of the recipe; the reader needs the tags to undo the cascade, a hand-written file has none (flags 1 to 3); 8 silent differences between "Python that runs" and "recipe that runs"; two hashes; refusal catalogue to maintain (~34 cases here); UI to show 10+ refusals | ADR-104 point 2, ADR-100 (one way to write), one authoritative form; FORMULA-SAFETY-1 extends to a file parser |
| **C. Neither** | nothing new | the independent reading, and the bugs it finds, are not available | |
| **D (variant, not built): read ONE call into ONE step in Blueprint** | most of the speed for a Polars user; no file, no tags, no cascade; the refusal list for steps is the part that worked | no plots; the user still needs the form | Blueprint only |

Where it would live (REASONED): the two-way call-shape table (method path, which argument is positional, namespace, which key is a list) belongs next to each action and component in its registry, so a new action cannot be added without it (a registry test, like DEC33); the pure writer and reader belong in `libs/utils` beside `formula_check.py` and `recipe_check.py` (no engine import; registries passed as plain data, spec section 14); the export wiring in `app/modules`. My prototype hard-codes the tables in `gen_python.py` (POSITIONAL_LIST, EXPR_NS, FUNCTIONS): the single-source version derives them from `wraps` and the schema.
Tests that keep it honest (generated Python equals the engine on every shipped recipe): per recipe, table by table and picture by picture (done here by script, about 4 minutes for 8 recipes, a slow test); a second recipe family with nulls, repeated keys, `na: keep`, seeds and every `modified` component (the shipped ones exercise few: all shipped `na` are `remove`); mutation checks by the reviewer (each of 6 above); a registry test that every action and component has its call shape; a staleness check (the file header carries the recipe hash and the data hash); for B, the round trip on every shipped recipe and a refusal catalogue test. The check also needs data where inner and left differ.
Security (READ spec section 15): the file is run on a user's machine; every literal is written with `repr`/`json.dumps` (no recipe text becomes code or a comment line), every formula passes `formula_problems` before it is written.
Effort (REASONED): prototype 410 + 620 lines in one session for 16 actions and 17 components. Production A for 68 actions and 191 components, tests included: about 1 to 1.5 weeks. B adds the reader for all call shapes, the refusal messages, the import screen in Blueprint and the tag handling: about 3 to 4 weeks, and a decision on what an imported file becomes (a new recipe draft checked by the same checker, never an update in place).

## Recommendation
A, built as a check of the engine and of the recipe, marked "generated, not the document", never read back. D later if Eve wants speed. Not B now: the silent differences of flags 1 to 3 and the hash change are design questions, not coding effort. Before A is built, decide #77 (DEC16) and the theme de-duplication bug, or the new test fails on shipped recipes (which is its purpose).
