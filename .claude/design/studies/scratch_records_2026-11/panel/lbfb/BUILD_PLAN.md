## 0. Flagged first: what changes a result silently, hides a step, or reconsiders a decision

1. **The walk may leave other tables that hold the same sample in place (OPEN, new, RAN).** D-0347 (decided) goes back from the chosen column to its sources and forward from them. For a sample id on the demo recipe this does not reach every table that carries the id. Starting from `sample_id` at the plot `mlst_bar` (`tmpAI/panel/lbfb/architect/closure.py`, table-level, every join of the demo keys on `sample_id`): one pass as D-0347 is written reaches 2 source tables and 13 of 17 plots; following the joins that equate the key on to the other ingredients reaches 8 sources and 15 plots; every source that declares the sample id as its key (`is_entity_key`) is 11 sources and 17 plots. From `amr_heatmap` the three figures are 1 source and 5 plots, 8 and 15, 11 and 17. So "remove sample S7, everything ticked" can leave S7 in 4 plots without any line saying so. This touches D-0347 (the three moves), D-0022 ("remove from all tables" is the one automatic placement) and D-0195 (no silent failure). Suggestion: the walk always returns, beside the lines, the list of source tables that declare the same key and that it did not reach ("same key, no join links them: not offered"), so the dialog says it; and the owner chooses which of the three scopes the lines cover. For the owner (question 1 of part 6).
2. **A filter step never changes a plan (RAN).** The engine's plan of a candidate copy gives the same names and types before and after a filter, and a wrong-typed value (a whole number compared with text) passes the plan and fails only when rows are read (`ComputeError: cannot compare string with numeric type`, run in this session). So "the state of each line comes from the plan of the candidate copy" is true for a drop and empty for a filter. A filter is protected only by the type per line (D-0202) and by the real run when it is applied.
3. **The key-drop rule as built is by column name for the whole recipe (READ `join_keys.py:328-339`, RAN `a1.py`).** `add_step` refuses a drop of `id` at all five places tried, also at the table of a plot that nothing reads. So the data scientist's legitimate case (drop `sample_id` at one plot only) is already refused today, and a dialog "with the key places grey" would show every place grey. Showing key places grey and ticking the others needs a place-aware rule: that reconsiders how D-0297 was built (its text only says a join key cannot be dropped). For the owner (question 5 of part 6).
4. **"Every place ticked" when the request starts from one plot (D-0194, D-0316) is the user's wrong-default case.** Not a conflict with the ledger text (D-0194 itself records "at usage we might change the default"); a wording and a possible later decision. For the owner (part 2).
5. **The plan cannot confirm a swap of two columns of equal type (RAN by the data scientist, `awk.py`/`mini.py`).** "Checked against the plan" (D-0351) is then true and says nothing. Suggestion: a rename whose keys and values overlap is shown grey. No shipped recipe has one (RAN `renames.py`: 8 renames in 7 recipes, none overlapping, none renamed back).
6. **The audit step is written at the END of its tier (D-0146).** A value computed earlier in the tier (a z-score, a rank, a mean) still holds the removed rows. The Walk carries this as data ("a step before this place computes across rows"); how it is said is OPEN (DESIGN question 23).
7. **Two stores of the columns (MINE).** `RecipeGraph.column_info` (declared fields, select, drop; `recipe_graph.py:276-289`) and the new plan record can disagree. The walk reads only the plan record; `column_info` is left to the checker (its only reader, `recipe_check.py:995,999`, RAN grep) with a removal task (part 3).
8. **A second code path for the plan (MINE).** `tmpAI/panel/column_tracking/measure/m.py` composes the plan with its own loop that copies the logic of `orchestrator._materialize_tier1`, `materialize_tier2` and `materialize_tier3` (READ `orchestrator.py:277-420, 507-565`) and uses private functions (`_read_source`, `_schemas_of`). Measured equal to the real run at 108 of 108 places on three recipes; a test that compares two paths cannot cover a recipe shape that no test recipe has (a tier 3 with steps, a pivot). Suggestion: the build and the plan share ONE composition function (step 0b).

## 3. The architecture of the mechanism (MINE unless a ledger number is cited)

### 3.1 Where the walk lives, and who may call the engine
- **The walk is one pure function in `libs/utils`** (the rule: the shared graph is in `libs/utils`, no Shiny, no import of a peer library; D-0031; `action_names.py` docstring says why constants live in utils: libraries that may not import `transformer` read them). Proposed files, all in `libs/utils/src/utils/`: `plan_book.py` (the types `Plan`, `PlanFailure`, `PlanBook`, nothing else), `step_effects.py` (the closed list, 3.4), `lineage_walk.py` (the walk and its records), `lineage_text.py` (the plain sentences, a separate pure function so that the words can be approved by the owner apart from the logic). Imports allowed: `recipe_graph`, `join_keys`, `action_names`, `plan_book`, `step_effects`. Forbidden and tested by an import test (DESIGN L076): `polars`, `app`, `transformer`, any file or clock.
- **Only the app layer calls the engine's plan.** A new `app/modules/plan_book.py` composes the plan (names and types of every step of every table, join and plot, and of every source) without building or storing, from the recipe in memory, and returns a `PlanBook`. The walk receives it finished as an argument. The handler (HOME's audit dialog) is the only caller of both. This is the same rule as `audit_run.py`, which lives in `app` and hands plain records to the layer above.
- **The injection is an argument, not the `columns_provider` hook (MINE; recommendation).** Why, all READ in `recipe_graph.py`: the hook is `f(node_id) -> names` (line 72), asked only for a node whose columns the recipe cannot say (282-288), so it gives names only (no types), one answer per node (no plan after step k, which DESIGN section 1b shows is needed to see "drop then create again"), and its answer is cached inside the graph (`_info`) so a second candidate copy would read a stale answer. It also hides a call to the engine inside what looks like a pure graph query. RAN grep: only two tests use it (`libs/utils/tests/test_recipe_graph.py:338, 347`); no production caller exists. As an argument, every input of the walk is visible in its signature: the walk is deterministic and a test can hand it a literal. Suggestion: `columns_provider` stays out of this work and gets a removal task or an owner's decision to adopt it (a deprecation has a removal task, `agent_principles.md` point 4).
- **Signature (proposed):** `walk(graph: RecipeGraph, plans: PlanBook, start: Start, kind: "filter" | "drop") -> Walk`, with `Start(node_id, column)` (the column's name at the END of the viewed node, DESIGN U4), and, for a drop only, `judge_drop(graph, walk, candidates: Mapping[place, PlanBook]) -> Walk`, where the caller supplies the plan of each candidate copy. No callback into the engine: the pure function stays pure and the candidate plans are built by the app.
- **The recipe given to the walk is the one in memory**: the audit copy when an audit is open (`build_graph(audit.recipe)`, as `audit_run.py:132` does), so audit steps are ordinary steps. The graph's `Node.steps` is already `recipe_tiers.step_list(...)` (author steps, then audit steps; READ `recipe_graph.py:489, 498-499`), so the walk reads nothing else. The audit-step test is its id (`audit_copy.is_audit_id`).

### 3.2 The data it returns (one record per line)
A `Walk` (frozen dataclasses, tuples and frozensets, no dict or set order ever iterated):
- `start`, `kind`, `lines` (tuple of `Line`, graph order), `gone` (tuple of `Gone`), `refusal` (None or a plain reason with its source, for example the key rule), `outside` (the sources that declare the same key and were not reached: information, never a line; flag 1), and derived counts `found`, `grey`, `gone` that are `len` of those tuples (D-0195). `found + grey == len(lines)`.
- `Line`: `place` (exactly the text `add_step` takes: `T1:<table>`, `T2:<table>`, `T3:<plot>`), `covers` (the collapsed nodes), `kind` (table or plot), `is_start`, `here` (name and engine type at the END of that place), `trail`, `state` (`tick` or `grey`), `reason` (a code from a closed list plus its parameters, never free text), `reach` (three frozensets: tables with a plot below, tables with none, plots; a count is `len`, never stored), `notes` (data, not sentences).
- `trail`: where it began (the source table and the column's name in the file, from `input_fields[...].original_name`) and a tuple of `Hop`: the node, the step number (counting audit steps after the author's), the action, the step's place in the recipe (`steps_path` plus the number; file and line when the function of D-0342 exists, it is not built: RAN grep found none), `is_audit`, and `how` in {unchanged, renamed, recomputed, cast, filled, key-equated, created, dropped, re-created, gone, unknown}, with the name and type before and after. A column that reaches a place by two paths (a join key present in both ingredients) has two trails; the place is one line.
- `Gone`: the place, the step that removed the column (or "not known"), a reason code (not kept by a select, dropped, key merged by the join, became values by an unpivot, became columns by a pivot), and the same `reach` flags, so the row change of that place is shown with it.
- Grey reasons (closed list, each with a sentence in `lineage_text`): the engine's plan failed at or above this place (with the engine's own sentence, D-0342, carried as data); a step the list does not know sits on the path; the prediction disagrees with the plan (D-0351); names exchanged by a rename; a join the list does not follow (a full join: DESIGN question 9); the data file is missing.
- Notes as data: name differs from the start's; type differs (both engine strings kept, so "exact" or "family" is a display choice, DESIGN question 10); recomputed or aggregated by step n (D-0353); filled; "a step before this place works across rows" (the actions in `action_names.POSITION_ACTIONS` plus group, unique, rank: INFERRED list, to be fixed in `step_effects`); left-join role (this table is the base, or the right table: removing a row of the right table empties columns and keeps the row; RAN by the data scientist: S3 stays in J1 with `country` and `year` missing).
- Example, the small recipe MR of the data scientist (RAN by him, `mini.py`), start `country` at PA: lines `T2:A` (here `country`), `T1:A` (here `origin`, trail: renamed by step 1 of A's tier 1, source `country`), `T1:J` (`origin`), `T2:J` (`origin`), "only PA", "only PJ"; `gone`: `T3:PK` (PK's own select keeps only `sample_id` and `mic`), still in the reach of `T1:A`, `T1:J`, `T2:J`; not a line: `T1:B` (its `country` is another column).

### 3.4 The three moves as one rule (so the code stays small)
The walk works on occurrences `(node, name)`. Edges: a step's effect from its name before to its name after (rename: mapping; select, drop: kept or gone; keeps-names actions: the same name; named outputs: created or recomputed), the edge from a table to the next tier, and, at a join step, the key pairs of that step (`left[i]` is `right[i]`) and the plain pass of a non-key column to the join's output (right-side name changed by the suffix when the plan says so).
1. **Back**: from the start occurrence, follow edges toward the sources until a source table's own column (or a creation step). This gives the source occurrences of the start column.
2. **Forward**: from every node of those occurrences, the reach is the graph's `lineage_forward` (a set of nodes, whether or not the column survives: DESIGN F-B, equals the nodes whose key changes when a step is written).
3. **Back again**: for every reached node, take its own path from the sources and apply the step effects forward to read the name there and the step that decides it. Each prediction is compared with the plan at that place (names and types). Agreement gives a line (tick). Disagreement, or a step outside the list on the path, gives a grey line with its reason. Absent in the plan with a known removing step gives `Gone`.
Two columns are the same only through a step or a join key pair of that join, never from equal names or equal types (DESIGN U1).
Collapse (D-0346, D-0343): a node with no steps (author or audit) is the table before it. A tier that holds only audit steps is NOT empty. A plot with its own tier 3 steps has ONE line `T3:<plot>`.
Order: graph order of the place (`RecipeGraph.nodes()` is topological and ordered by recipe position; `lineage_forward` returns `sorted(..., key=index)`, `recipe_graph.py:208`). The start's line carries `is_start`; moving it first is a display choice (DESIGN question 11). The walk never iterates a set.

### 3.5 What it must NOT do
Guess (a rename from "one gone, one new"; an identity from equal names). Return fewer lines silently: the invariant (DESIGN L087) is that the nodes of the reach equal the nodes covered by lines, `gone` and greys, tested on every fixture and recipe. Read a row, a file or the clock. Change the graph, the plan or the recipe. Count rows (the engine counts, D-0316). Raise for one failing place: that place and what is below it are grey with the engine's sentence; a node missing from the plan record altogether is a bug of the caller and raises, by name, so absence is never read as failure (the builder writes an explicit `PlanFailure` for every node below a failure).

### 3.6 The plan of a candidate copy, and what it costs
Why for a drop: a drop removes the column below; whether that breaks a later step or a join key is answered exactly by the engine's plan of the copy, with no parsing of expressions (the data scientist's proposal, which I support, `scientist.md` B.4). A plot that draws the column is found from the plan of its table and `RecipeGraph.plot_columns` (`recipe_graph.py:374-388`). For a filter it adds nothing (flag 2).
Counts, for a dialog with N lines:
- Filter: 0 extra plans. One baseline plan record for the recipe, built at opening with everything else (D-0326), cached by the recipe's keys (DESIGN U9) so an added or removed audit step recomposes only the place and what is below it.
- Drop: N + 1 candidate plans (one per tick line, one for all ticked).
- Cost, RAN (`cost.py`, the worktree code of `task/slice-c-audit-form`, lazy plans, nothing collected or stored, one filter step as the candidate): demo recipe, baseline plan 0.086 s plus 0.040 s to read the sources once, 91 schema calls; 58 candidate copies: recomposing everything each time 3.2 to 3.3 s in total over two runs (mean 56 to 58 ms); recomposing only the place and what is below it, with the lazy frames above it reused, 0.25 to 0.33 s in total (mean 4 to 6 ms, largest 30 to 50 ms). Figshare recipe: 8 candidates, 0.02 s and 0.01 s. `1_Abromics_general_pipeline`: 0.10 s and 0.04 s. Stress recipe: below 5 ms. So one plan per candidate is affordable (46 lines on the demo is about 0.3 s). It should still be cut in two ways, which are cheap: compute candidates only for a drop, and only below the place. Not measured: a recipe with a pivot (the plan reads rows to that step, DESIGN L080), the rows-affected count per line (a real run per line; DESIGN says unmeasured, needed for question 16), larger data. The time to read the sources grew from 0.02 s to 0.22 s with the data in the earlier measurement (`TABLE_FOR_THE_OWNER.md`).

### 3.7 How it relates to `audit_copy.add_step` and `audit_run`
- The walk never writes. The dialog calls `add_step(audit, place, step, comment)` once per ticked line with `Line.place`; `add_step` stays the one gate (a filter or a drop, key rule, reason). The line's value is typed per place by the dialog (D-0202), from `Line.here.type`.
- `audit_run.run_audit` gives the affected plots and which tables are rebuilt (`audit_run.py:96-112`, `TableRun`, `PlotRun`); it gives no row counts per table today, which D-0316 asks for. That is a separate step (part 4, track R), not the walk's job.
- The walk run on a copy that already holds audit steps reads them as steps (3.1). A drop audit step made earlier removes the column below it, so a second dialog offers no line there (DESIGN L066).

### 3.8 What an audit or a test would not catch (say it to the builder)
- A plan record that is right for the shipped recipes and wrong for a shape they lack (a tier 3 with steps, a pivot, a join clash): only the small fixtures cover those, and only if the plan builder is run on them (DESIGN section 3.1 lists what the shipped recipes lack, RAN `steps_census.py`: 131 steps in 7 recipes, 17 actions, no `suffix`, no overlapping rename).
- A prediction that agrees vacuously with the plan: a swap of equal types, a cast to the same type, a `with_columns` that rewrites a column in place with its own type (DESIGN F-C).
- Identity of numeric columns on real recipes (the marker oracle marks text only).
- The dialog writing a different step from the one the walk reasoned about (typed value, kind): needs the engine tests with the real `add_step`.
- Name-based key families used by a later change as identity.
