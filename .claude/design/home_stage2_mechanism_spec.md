## A3. What your decisions since 2026-11-13 changed in this plan
- Missing values: every filter states `na: keep|remove`, the engine follows Polars (ADR-103, 2026-11-14). The audit writes `na` in every step.
- A filter value has the type of its column; a wrong type is a plain error, never converted silently (ADR-104 point 7, 2026-11-14). v0.1 said "converted per node, a warning": now an error at that place.
- Every operator is usable, `between` with its four ends; Date gets a date picker, Boolean a two-choice control, text no greater/less; Time and Duration need controls (ADR-104 point 4 and its note of 2026-11-15; FILTER-PICKERS-1).
- No silent error: a step that cannot run is an error, never skipped; the plot follows the table (ADR-104 point 1, 2026-11-14; PLOT-TABLE-ORDER-1).
- Seed: a recipe's seed holds, the default is 0, HOME draws no seed per session (ADR-104 point 3; decision of 2026-11-15). The export legs record the seed.
- The audit acts along the lineage, on the places you tick; exploration acts only on the data viewed (ADR-105, confirmed 2026-11-14). Same as v0.1, now recorded.
- Steps stay lists; the audit marker is `id: audit_<8 hex>_<k>`, only in the `audit` profile (DEC18, 2026-11-13). This closes the v0.1 discussion of dictionaries and the open marker.
- The published columns of a table are its last tier-1 `polars_select` (DEC23, 2026-11-13; built `c827d335`): a T1 audit step is written after it, so it sees the columns you see.
- The audit writes `modif_filter` (`column`, `op`, `value`, `na`) and `polars_drop` (DEC39, DEC37, 2026-11-13).
- A table plotted directly runs its own tier 2 (DEC16; built `eafc570c`, 2026-11-15): every table has a T2 to write into.
- Blueprint may write a plot's tier 3 (note at ADR-100, 2026-11-15): the original may already hold tier-3 steps; audit steps go after them and carry the marker.
- Join keys keep their declared types (ADR-102, 2026-11-14); a self-join runs with a warning (D8, 2026-11-15); one join-key rule in `libs/utils` (D7, 2026-11-15). The graph uses that one rule.
- The plot library follows the recipe standard; a plot that cannot be drawn shows its error in its place (ADR-106; built `c442af4c`). The audit view reuses it.
- One source of truth wherever a rule exists in several copies (D7, 2026-11-15).
- A build on a recommendation may be PROVISIONAL when no result changes silently and nothing is hidden (2026-11-15, `tasks.md` rules).
- `hypothesis` is decided after this document is confirmed (D15, 2026-11-15).

## 2. Data structures
- **Node id** [MINE, question 7]: `DS:<dataset>`, `T1:<table>`, `T2:<table>`, `T3:<plot>`; a node's `columns` come from the stored schema (parquet metadata) or a dry run on the column names, never from computing the data [CODE: Polars `collect_schema`]. A T1 node's columns are those of its last tier-1 `polars_select` (DEC23).
- **User step** [DECIDED, 5a-1..3]: `{id, kind: filter|drop, field, op, value | values, nodes: [node id], reason, initials, created_at}`. ~~The value is converted to each node's column type (`FILTER-DTYPES-1`).~~ (superseded 2026-11-14 by ADR-104 point 7: the value is stored in the column's type, never converted silently; a wrong type is a plain error.) **Now [DECIDED]:** a filter step also carries `na: keep|remove` (ADR-103 points 2 and 8) and, for `between`, `closed` (ADR-104 point 4); the value is typed per node from the schema of the table at that node (ADR-104 point 7); a node where it cannot be typed is shown with the error and cannot be ticked [MINE, question 3].
- **Audit copy** [DECIDED, 5a-22]: the resolved single-file recipe (all `!include` merged, `plots` mirror removed, as `build_mode2_recipe` does today, `t3_translator.py:212` [CODE]) in the session folder `_sessions/<session key>/audit/<recipe id>.yaml` (path [MINE, question 7]); header: the original's file-set hash and the recipe format version (`spec_version`, DEC04); ~~each audit step carries the origin marker [RECIPE: name and shape to set]~~ (superseded 2026-11-13 by DEC18). **Now [DECIDED, DEC18]:** each audit step carries `id: audit_<8 hex>_<k>`; the copy passes `check_recipe` in profile `audit`; **invariant: the copy minus its marked steps equals the original; any difference blocks** (5a-22; AUDIT-VIEW-1, 2026-11-13).
- **Insertion**: the end of a table's tier-1 list (T1), tier-2 list (T2) or the plot's T3 list; the action is a named, parameterised action, never formula text from user values [DECIDED, 5a-14]. **Now [DECIDED]:** a filter is `modif_filter` (`column`, `op`, `value`, `na`; DEC39), a drop is `polars_drop` (DEC37). T1: after the table's last step, so after its `polars_select` (DEC23). T2: a join's `steps.tier2`, or the `wrangling.tier2` of a table plotted directly (DEC16, built `eafc570c`). T3: the plot entry's `steps.tier3`, after the steps the maker wrote there (DEC17; note at ADR-100, 2026-11-15). At one place, filters before drops [MINE, question 2].
- **Series key** [DECIDED, ADR-101]: labelled parts in execution order, `E . rC . dC . [a1] . [s2] . [a2] . [s3] . [a3]`, 128 bits per part, an empty part omitted; the parts `a` come from the operations of the marked steps only (the `id` and `comment` of a step are not hashed, recipe spec 7.5). T1 per table with precise parts from the graph; a table whose inputs cannot be listed safely keeps a coarse part (fail-safe). **Today [CODE]:** one T1 key for the whole recipe (`cache_keys.py:90-91`), an empty tier-2 list changes the key (`cache_keys.py:94-95`): P4 changes both.
- **Event** [MINE, question 7]: `{ts, initials, type: created|removed|reverted|ack_warning, step id, payload}`; replaying the log gives the copy's marked steps (a test). Exported (ADR-101 point 5; see A4 b).

## 3. Algorithms
1. **Candidate nodes for a field** [DECIDED, ADR-105 point 2]: `graph.nodes_with_column(field)` along the open plot's lineage and, for the whole recipe, every node; ticks default to all; suggestions from `shared_columns` (the join key families, from the one join-key rule, D7); the key is information (counts, the warning on a join key), not mechanism (ADR-105 point 3).
2. **Compile**: for each ticked node, one insertion; ~~the filter value converted to the node's type~~ (superseded 2026-11-14 by ADR-104 point 7: typed from the node's schema, a wrong type is an error); drop uses the same logic (`home_audit_steps.md` 9). A filter on a column that an earlier audit step dropped at that place is refused at recording (PLOT-TABLE-ORDER-1, Eve 2026-11-14).
3. **Trial = Apply** ~~[DECIDED, D2]~~ (corrected 2026-11-15: the tag "D2" of v0.1 points to no traceable record; the rule is ADR-105 point 4, one candidate step previewed in a dialog, Apply with a reason adopts it, Cancel changes nothing) [DECIDED, ADR-105 point 4]: the dialog compiles the candidate into a temporary copy, runs the affected nodes through the audit orchestrator, shows counts before and after and a preview of the open plot, and discards it; Apply persists the same copy, so the nodes are reused by key and nothing is computed twice (the reuse is [MINE, question 7]).
4. **Step-by-step counts** [DECIDED, SC2 2026-11-12; 5a points 17, 18]: start at the population table (`entity.population`, else the distinct keys of the first node that has the key); each step is applied to the result of the steps before it, with a probe (rows, entities by key, missing values in the filtered column among the removed rows, counted on the table the filter acts on, ADR-103 point 10); derived, never stored; the report snapshot is recomputed by the import. The join counts of JOIN-COUNTS-1 (PROVISIONAL, channel L32) are read here when they exist.
5. **Checks after Apply** [DECIDED, 5a-12]: the same condition is evaluated again on every node that has the field and the result is shown.
6. **Re-base** [MINE, question 5]: if the original or the data changes while audit is open, the copy's origin hash no longer matches; the export is refused; "re-base" writes the marked steps into the new original at the same nodes and gives each step a status (applied, not concerned, broken).
7. **View** [DECIDED, 5a-22]: Exploration reads the original recipe and orchestrator; audit mode reads the copy and the second orchestrator; Compare reads both. `active_cfg` (about 35 uses) and `orchestrator.` (about 12) are replaced by the view pair; a test checks that in audit mode no handler reads the original [CODE counts, 2026-11-13]. **Recount 2026-11-15 [CODE]:** 34 lines with `active_cfg` and 14 with `orchestrator.` in the HOME handlers (Blueprint left out). A plot that cannot be drawn shows its error in its place (ADR-106 V7, `c442af4c`).

The safeguards for the keyed containers `analysis_groups` and `plots` are in RECIPE-ORDER-IDS-1: repeated keys refused, built in `utils/strict_yaml.py`; writers keep the key order.) The facts below apply only to the keyed containers `analysis_groups` and `plots`. This spec assumes ordered lists in three places (insertion at the end, the hash of the steps, the copy-minus-marked-steps invariant). Three facts, verified on 2026-11-13, that a dictionary form must handle: (a) a duplicate key in YAML silently keeps the **last** one, so a duplicated step name drops the first step without any message: the loader must refuse duplicate keys; (b) `canonical_hash` sorts dictionary keys, so two orders of a dictionary of steps give the **same** key: the steps must be converted to an ordered list (file order) before hashing and before the engine runs them, in one place (the loader or the graph), never at the call sites; (c) `yaml.dump` sorts keys by default and several writers do not pass `sort_keys=False` (`exporter.py` twice, `blueprint_handlers.py`, `wrangle_studio.py`, to check call by call): a writer that sorts would reorder the steps silently; a test must scan the writers, or the order must come from an explicit field instead of the mapping order. A dictionary also helps: the step name is a stable id (for the origin marker, the integrity check by key, the removal), and a comment can sit on a step. Decision for the recipe session; this spec then adapts: the insertion adds a key at the end, the marker can be the key's prefix, the invariant compares by key. **My recommendation (2026-11-13): ordered steps stay lists; things that have a name stay dictionaries (data schemas, joins, plots, groups, fields); a step that needs a stable id carries an optional `id` field inside its list item.** That removes (a) to (c) for steps and keeps the ids and comments; where the order of a dictionary matters (tab order, column order of `input_fields`), the recipe session decides whether the order is part of the key.
