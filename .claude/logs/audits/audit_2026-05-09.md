## Wave 6 — Library dependency model clarification (later in session)

**Design decision:** Two-tier library dependency model formalized and propagated.

- `libs/utils/` = **base layer** (stdlib + polars only; importable by any domain lib; must be declared in `pyproject.toml`)
- All other `libs/` = **domain layers** (zero peer-to-peer cross-lib imports; independently reusable)
- `app/` = **orchestration layer** (only place that wires multiple libs together)

**Rationale:** Each domain lib must be usable standalone — different UI (CLI, API, Galaxy) can import only the layers it needs.

**Terminology fix:** "data-agnostic" was ambiguous. Replaced with:
- _Manifest-driven_: no hardcoded domain knowledge (species, gene names); all behavior injected via manifest/config at runtime
- _Domain-agnostic at the import level_: no cross-lib peer imports

## Phase 32 / ADR-076 + ADR-077 + ADR-078 + ADR-079 (afternoon session)

### What was decided

**ADR-076 — BLUEPRINT AI Agent Helper** (revised from earlier draft this morning)
- Three adapter backends: `ClaudeCliAdapter` (Phase 1 — uses local Claude Code subscription, no API key), `ClaudeApiAdapter` (Phase 2 stub, ANTHROPIC_API_KEY), `LocalModelAdapter` (Phase 3, Ollama/LM Studio).
- All backends buffered — **streaming explicitly out of scope** for Phase 1 (user confirmed: "ok, without streaming").
- New §10 Tool-Call Mechanism: `claude_cli` uses an HTML-comment-marked fenced JSON block protocol because `claude -p` does not expose user-defined tools (only Claude Code's own). MCP server is the deferred Phase 2 migration path.
- New §11 Subprocess Isolation: every agent session runs with `cwd={project_root}/agent_sessions/{uuid}/` so `claude --continue` cannot collide with the user's terminal Claude Code conversation. `flock`-based single-flight + auth probe at init.
- Persona config block, 7 tools, 3-tier data visibility (off / schema_summary / full_sample), per-session `agent_sessions/{uuid}/` bundle (conversation.jsonl, report.qmd, manifest_sha256.txt), Two-Category Law placement under `libs/blueprint_arch/`.

**ADR-077 — No-Silent-Suppression principle**
Authored after the user pushed back on the silent cascade pattern: *"silent failure / silent suppression usually not desired."* Group D cascades (`manifest_edit_enabled`, `blueprint_agent_enabled`) are now **fatal** validator errors instead of silent bootloader rewrites. Groups B and C (interactivity, import_helper) remain soft for backward compatibility — explicitly justified. General principle established: *"Silent suppression hides bugs. Silent rewriting hides intent. The default response to a contradictory configuration is to halt with a clear error."*

**ADR-078 — Diagnostic Error Discipline**
Establishes operator-readable error blocks. `DeploymentError` dataclass with five fields (component, problem, location, fix, who) plus optional reference + related. `format_errors_block()` and `exit_if_errors()` helpers in `app/modules/deployment_error.py`. Phase B (delivered): PersonaValidator + server.py + CLI script retrofitted. Phase C (committed work, not optional polish): SidebarValidator, Bootloader, Connectors, Manifest preflight, Troubleshooting Catalog, CLI scripts.

**ADR-079 — Runtime Error Discipline (placeholder)**
Stub authored to lock in the runtime-error problem. Distinct treatment from ADR-078 because the audience (analyst, not operator), fix surface (data/manifest, not config), and render path (Shiny notification / plot card overlay, not stderr) differ. Targets ingestion / assembler / wrangler / viz_factory / T3 apply / Blueprint manifest validation. To be authored when Phase C is largely complete OR when the first runtime-error pain point becomes blocking.
