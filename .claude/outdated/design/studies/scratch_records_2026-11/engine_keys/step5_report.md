## What is true now, point by point

**1. Every registry entry carries `engine`.**
- `ACTION_ENGINES` (`libs/transformer/src/transformer/actions/base.py`) and `COMPONENT_ENGINES` (`libs/viz_factory/src/viz_factory/registry.py`) are filled by the decorators. The decorator keyword `engine` defaults to the library's engine (`DATA_ENGINE`, `PLOT_ENGINE`); a value the app has no library for raises `ValueError` ("... no library for this engine in this app ...") and nothing is registered, so no entry can lack the field. `modif_` and `step_` entries carry it in the field only.
- Tests: `libs/transformer/tests/test_action_engine_field.py` (11), `libs/viz_factory/tests/test_component_engine_field.py` (11): registry and field have the same names (68 actions, 191 components today, all `python-polars` / `python-plotnine`), field and prefix agree (`utils.engines.prefix_problems`, `polars_`; `plotnine_` has no entry yet, the rename is on hold and untouched), unknown or empty engine refused and not registered, a refused schema leaves no engine behind, a second registration replaces the engine.
- Fail-once (`tmpAI/breakonce5.py` in the worktree, output `tmpAI/breakonce5_out.txt`): decorator stores no engine: caught (both libs); decorator accepts an unknown engine: caught (both libs); prefix check finds nothing: caught.

**2. One entry file per library.**

- The table of the engines is `utils.engines.ENGINE_TABLE` (engine, recipe key, library, name prefix); `ENGINES` is derived from it. File name = `engine_` + value with `-` turned into `_` (`engines.entry_module_name`).

## Missing decisions and open choices (not decided by me)
1. **Tier 3 and "an engine the audit cannot write" (brief 3d).** The ledger says (D-0237 point 4): tier 3 gets the key and "another value is refused with 'no library for this engine in this app'". The plan (sections 2.2 and 2.4) says the audit writes Polars steps, so tier 3 stays Polars. Today only one data engine exists, so T06 already refuses every other value at tier 3 (tested at `...tier3.data_engine`). What no decision states: on the day a second DATA engine exists, may tier 3 name that engine (the app has a library for it), or only the engine the audit writes (`python-polars`)? Options: (a) any data engine the app has; (b) only `python-polars` with its own message. I built nothing for it.
2. **A recipe that names no engine at run time** (the checker refuses it, T04; the spec has no default). The orchestrator and the plot dispatcher refuse it too ("names no data_engine / plot_engine"). PROVISIONAL: I read "never a silent fall back" as covering this. Option: let the code below the gate (scripts, tests) use the library's engine when none is written.
3. **`PlotEngines.default_random_state`** (the seed HOME shows and the export records) is the seed of the one plot engine the app has (`utils.engines.PLOT_ENGINE`). PROVISIONAL. With a second plot engine the seed belongs to the plot's engine and `seed_in_use` and `export_seed_plan` need the plot's engine.
4. **Ingestion is not part of the data `ENTRY`.** The plan listed `ingest` too, but ingestion is another library (`libs/ingestion`) and the libraries do not import each other; `DataIngestor` stays chosen by the orchestrator and is not an engine choice.
5. **Two layers for the plot's engine.** HOME and the export (and Blueprint) still put `plot_engine_slot(...)` in the dictionary (step 4b), and `PlotEngines.render` now resolves the same value itself. They agree, but it is two ways to do one thing. Option: remove the slot from the three builders and from `test_plot_engine_reaches_the_factory.py`, so the dispatcher is the only one. I left it (4b's work, tested).
6. **`libs/*/tests/debug_*.py`** runners (transformer, viz_factory) still build their own library's classes directly (they are the libraries' own debug tools); `libs/viz_factory/tests/debug_runner.py:72` imports `DataWrangler` of the transformer (a cross-library import in a test script that was there before; the cross-lib audit does not report it).
7. **`DataWrangler.tier_steps`** is still called directly by the validator and by Blueprint's node click: it reads the written shape of a tier; it does not run a step. Only the orchestrator, which runs, goes through the entry.
8. **Step 6 (cache keys) is not built**: today the engine of a tier is in no cache key, so changing only the `data_engine` of a tier would serve the stored table of the other engine. With one data engine nothing can differ; it must be closed by step 6 before this branch is merged.
9. The empty orphan `experimental/test_logic.yaml` (0 bytes) is still in the config tree and now shows a longer rejection text (see proof 1).
