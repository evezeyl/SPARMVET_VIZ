# One place that catches Polars failures: where we are and the options (D-0260; asked in the review session's message of 09:15)

Digest by the coordinator of a scout's survey, 2026-11-18. The scout READ the code; it ran nothing.
Where a line says "not run", a small run is still needed. Nothing is built. The design is not decided.

## What a user meets today

- A Polars failure can reach the user in at least 14 places. There is no single place. Each place writes its own text.
- In several places the user reads the raw Polars text:
  - on a plot: "Data error: ..." and "Render error: ..." (`home_theater.py:482,528,600`);
  - in the data preview: a table with one column "Error" (`home_theater.py:1413-1415`);
  - the box "Data Assembly Failed" (`home_theater.py:897-906`);
  - the Blueprint join preview: "Preview failed: ..." (`blueprint_handlers.py:211-212`);
  - in an export: the files `*_ERROR.txt` (`export_handlers.py:1306,1326-1331,1361-1366`).
- Most of these do not name the step. Reason: Polars works lazily. The failure shows when the table is finally computed, far from the step that caused it.
- The step IS named where the plan is built inside the step (`data_wrangler.py:133-162`, `data_assembler.py:298-404`).
- A Polars "panic" (an internal crash that Polars reports) is handled in only three places today (`data_assembler.py:374`, `anchor.py:130`, `polars_aggregations.py:63`). Elsewhere it passes through.
- About twelve places swallow an error with no word to the user (list below).
- The app writes no log file. Raw texts go to the console only.

## What can and cannot be caught

- Every ordinary Polars error can be caught.
- A panic can be caught. OPEN FACT: the code comments say a panic is of a kind that a general "catch all errors" misses; the Polars type file says the opposite. Nobody ran it. One line run settles it (first thing a builder runs).
- NOT catchable from inside the app: Polars ending the whole process (its time limit), the system killing the app for memory, a crash in native code, a hang. Only running the engine in a separate child process contains these. The app already does this once, for Blueprint's Validate (`validate_runner.py:21-59`).

## Options

| Option | What it is | Good | Bad | Effort |
|---|---|---|---|---|
| a | One helper that every "compute the table now" call goes through | one place; a test can forbid any call outside it | the step is unknown at most of these calls; about 25 edits | [sonnet/high] |
| b | Catch where the step runs, plus the helper of (a) for the app's own calls | the step is named where it is known; smallest change to the engine | the other places still need the helper | [sonnet/high] |
| c | A catch at the screen boundary (every output of HOME, Export, Blueprint) | catches what nobody thought of | knows the plot, not the step | [sonnet/medium] to [sonnet/high] |
| d | Combination: the step is added where it is known; ONE function turns any Polars failure into the plain message and writes the raw text to a log; the screen boundary is the safety net | names the step when it can; one translation; raw text kept; catches the unexpected | most edits; needs the log decision first | design [opus/high], build [sonnet/high] |
| e | The engine in a child process (only for the "process dies" case) | a crash becomes a plain message, not a dead session | slower start per table; new things to test | [opus/high] |

The scout recommends (d), with (e) later. This is a recommendation, not a decision.

How the step can be named despite the lazy computing (three ways, they can be combined):
1. check the plan after each step (names plan errors, not value errors);
2. run each step on one row at check time (names more, cheap, misses errors on other rows);
3. when a later computing fails, say honestly "one of steps 1 to N of table T".

## Tests the build must have (each must be able to fail)

A missing column at step 3 of 5 names recipe, table, step, column and has a suggestion. A type mismatch in a join names the join. A panic from a known case gives a message without the words "panic" or "Rust", and the log holds the raw text. The plot, the data preview and the export error file show the plain text. Stop signals of the program pass untouched. A failure of the log does not hide the first error. An audit step error keeps its own text. No "compute now" call exists outside the helper. One test per place that swallows an error today.

## Infinite and not-a-number values elsewhere (D-0261 point 4; code read, not run)

- They come from ordinary formulas (a division, a log, a square root) and from the plot function.
- Plots: plotnine drops not-a-number points and gives a warning that the app does not show. It does NOT drop infinite points.
- Filters and summaries follow Polars: a not-a-number counts as larger than every number; sum and mean of a column with one become not-a-number; min and max ignore it. This is documented in the engine, not warned.
- The missing-value counts of the filter dialog count "no value" and "not a number" separately. Infinite values are counted nowhere.
- How they look in the data preview and in an exported table: not run.
- To run (small): the kind of a panic; `1/x` at 0, log and square root of 0 and -1 through a recipe formula; a filter above and below on such rows; mean, median, min; the exported text; the plot function `1/x`; the missing-value count of an infinite row.

## What nothing decides (for Eve), in plain words

1. When the engine itself dies, what does the user read? Default: "The engine stopped while it built <table>. The table was not stored. Suggestion: run it again; if it stops again, report the recipe and the data size."
2. Is the raw Polars text also offered to the user under a "details" fold, or only kept in the log? Default: log only.
3. Where does the log live? Default: one file per day in the user-data folder of the deployment, with recipe, table, step and time.
4. When the step cannot be known, may the message say "one of steps 1 to N"? Default: yes, and it says so plainly.
5. Which word for the remedy everywhere: "Suggestion:" or "Fix:"? Default: "Suggestion:" (D-0099); the plot library and its tests follow.
6. The child process for the engine: now or later? Default: later; until then a dead engine is a known limit, written in the docs.
7. Which option (a to d)? Default: d.
8. For infinite values in plots and tables: should the app warn, as decided for the plot function (D-0261)? Default: yes for plots (one visible warning per plot, with the count); tables: show the count in the missing-value lines.
