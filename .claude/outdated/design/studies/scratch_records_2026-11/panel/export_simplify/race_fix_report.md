## Mechanism (five lines)
1. The server tells the page its session with a keyed message `export_session {key, values?}` (`_tell_the_page_its_session`, priority -50, after the work of a recipe switch). With `values` (session changed) the page puts them in the panel through the inputs' own bindings and takes the key in the same JS step.
2. The recipe selector is now watched like an Export field (`EXPORT_WATCHED_FIELDS`): the page greys the button at the selector's own change event (user or server-set), before any server answer. This is how the page learns a switch by any route (selector click, load gate `update_select`).
3. The page reports each change the USER makes as `export_field_change {key: pageKey, field, value}`; values the server set are never reported. The server stores under that key (`ExportFieldsStore.remember`, only for a key it announced; empty or unknown key = dropped, with a warning notice for an unknown non-empty key), never under the key that is current on arrival.
4. The echo carries `key` (the session the server last announced); the page opens the button only if that key is the one it was told last, the selector it shows equals the server's, and all fields equal the screen. The old per-field `_remember_one` effects, `_set_on_page` and the compare-with-server-input push (the root of F2) are removed.
5. Fallback unchanged: 5000 ms, same texts (`EXPORT_READY_TEXTS`).

## Cases not covered / limits
- LONG FLUSH (real, open): when the server needs more than 5 s for the work of a switch, the existing 5 s fallback opens the button before the server confirmed. The page then shows the old fields next to the new recipe, so a press in that moment can still mix (as before the fix), with the existing notice shown. demo_abromics is at 4.9-5.0 s on this machine, so a slightly larger recipe crosses it. The brief forbids changing the 5000 ms or the texts. A real close would be a server-side check in the download (the values the download reads equal the remembered values of the session it exports). I did not build it: it needs the three headless download harnesses to feed the store (large test change) and a decision of yours.
- A press already on its way to the server at the instant of the switch exports the recipe left, with its own values (consistent, 1 of 20 in the review).
- Not tested: a data change under the same recipe (new data hash), session restore and import in the browser, two tabs after this change, Firefox/Safari, a press with a real mouse in the window.
- Unproven change I tried and removed: treating a missing field as its default in the echo (no test could show it was needed).
- The lock effect: pings wait for the reactive lock, so after a switch the grey time is the server time of that switch, by design.
