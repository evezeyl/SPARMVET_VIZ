## Part 2: the second defect (verified / inferred)
Facts verified
- Shiny 1.6.0 code: the WebSocket handler takes the reactive lock before it applies an input message (`shiny/session/_session.py:661` `async with lock()`, then `_manage_inputs` at :692/:717); the download request is handled at :908-916 inside `session_context` + `isolate()` with no lock. So a download can read the inputs while a message is not applied yet. This is Shiny's design, independent of this branch.
- Wire evidence (builder's runs and mine): in lost runs the page sent the box message ~0.1 s and the label message right before the click (e.g. dev r7: 11.781 box true, 11.892 label, no other message until 38.1 s after the download), no redraw message, the zip has no reproducibility folder and the folder name is `_user`: both inputs were still the defaults when the handler read them.
- It is also visible mid-stream: dev r1 and several others: the box was read as ticked but the label as default (folder `_user`, reproducibility part present): the download was read between two ws messages. This proves the order problem (HTTP before ws), not only "slow".
- Same race on dev (verified): alternating runs of the seed test, 12 each, same machine, one after the other: dev 2/12 failed (r7, r10: pure race, no redraw message in the wire log), branch 3/12 failed (r1, r4, r6). Label lost: dev 10/12, branch 6/12.
- Rate: builder 16/58 failed over four batches on the branch, my 3/12: 19/70 (27%). Dev: the controls report 3/34 plain (9%) and 0/14 with wire log, my 2/12: 5/60 (8%). The pooled difference looks significant (Fisher p 0.0065) but it mixes different days and loads; in my alternating runs it is not (2/12 vs 3/12, p 1.0, no power). So: branch higher in the pooled numbers, not proven in a controlled comparison. Reasoned only: dev's redraw adds failures of its own, so the branch should not be worse for that reason; a faster page (no redraw) giving a faster click is the builder's idea, I did not prove it; the label counts (dev loses it more often) do not support it.
- How fast must a person be (fresh app, the test steps with a pause between tick, label and click; pause applied after the tick and after the label): 0 ms: box lost 2/8, label lost 3/8; 300 ms: 0/8 and 0/8; 1000 ms: 0/8 and 0/8. Warm session, repeated export (24 trials, pauses W/0/100/250/500/1000, 4 rounds): 1 lost, at 0 ms; 0 lost at 100 ms and more. So the window is under about 300 ms after the last change. A person who ticks and then moves to the button needs more than that; a person who types a label and clicks Export directly: the field sends on change/blur at mouse-down, within milliseconds of the click (inferred from Shiny's text input behaviour, not measured with a human), so the label is the likeliest to be lost, then a load-dependent loss of the box. The server being busy lengthens the window (inferred: messages sent 100 ms earlier were still not applied).
Inferred / not proven
- Why a message sent 0.1 s earlier is not applied when the download starts: not shown. A busy event loop with the socket not yet read is my reading. I tested the lock idea in a scratch copy: the handler first `async with reactive.lock(): pass`. It did NOT cure it: 2/12 lost (r5, r9). So queueing for the lock is not the only cause (n=12, a small test).
