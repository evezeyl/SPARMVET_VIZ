## The question
When the dialog of an audit step (and of "remove from all the data") opens, which places start ticked?
- **A** (her new idea): only the EARLIEST place of each branch (tier 1 of each original data file the sample comes through); the later places are listed, unticked, tickable.
- **B** (her earlier decision D-0316): every place the step can reach is ticked; the user unticks.
- Add an option if you see a better one (for example A with one extra rule for the cases where earliest-only is not enough).
And the feedback the dialog gives, which she wants reduced to what matters: which NUMBER is shown per table so that it is always true. The trial computed three: rows removed by the step written there given the other steps (0 at every later place when everything is ticked); rows removed if the step stood alone; rows of the table before minus after. It found that the pair "rows that hold the sample before / after" is true in every case run, and "removed" alone is not.

## Facts of the trial you must weigh (details and numbers in TRIAL.md)
1. On the demo recipe A and B give IDENTICAL results in all 73 tables, for six sample cases. A writes 11 steps, B writes 27.
2. Earliest-only is NOT always enough, on small test recipes: (a) the key exists only in the RIGHT table of a left join (the left table holds another column): the row stays in the left table and in the join under A and under B, and the library says nothing; (b) a join recomputes the key from a table that is not a place: A leaves the sample in the join, B removes it (the only A against B difference found); (c) a table that holds the key under another column name, with no join linking it: invisible to the app; (d) the typed value does not match what a place holds (a key lowercased or copied in upper case by a step): the sample stays under A and B; the library warns for the lowercased key and is silent for the upper-case copy; (e) a key of different types in different tables: the whole choice is refused, nothing is written.
3. "N = 0 means wrong place" misleads as stated: under B the step written at each of the 16 joins removes 0 rows because the earlier steps already removed them; N = 0 is also true where the sample was never in the table; N > 0 can stand beside a row that stays (case a). It does catch a rewritten key at that place.
4. The left-join case she was told about (only the second table filtered: the first table's row stays with empty columns) is real on the demo when the user ticks one source only, and disappears under A because every source is ticked.
5. The library's present warnings on the demo: 6 tables listed "the sample may stay" and all 6 are false alarms; under A 16 joins would be listed "stays by your choice" although the sample is gone from all of them.
6. A table that computes across samples: A and B agree; if the user ticks only the join (not the source), the count of rows removed is the same but the other samples' values differ. A number cannot show this.
